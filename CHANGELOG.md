## [1.1.0] - 2026-09-25

### Changed
- **The AI assistant prompts are dramatically leaner (less AI token usage per run) without losing any decision rules the AI needs to build forms/workflows correctly.** Three new lean prompt variants were added and wired into the run pipeline, so every pass in `AICodBiAssistant` now sends only the decision-relevant core instead of the full general reference:
  - **Workflow pass** (`loadCodbiApplyPrompt`) now uses the new `formcycle.general_apply` (workflow-apply decision core) and `formcycle.general_workflow` (workflow creation/edges decision core) instead of the full `formcycle.general`.
  - **Blind rethink pass** (`loadCodbiRethinkPrompt`) now uses the new `codbi.general_rethink` — a content-faithful combination of the decision core plus the cross-cutting build-syntax annex (datatype-regex wiring, combining functionalities, panels-folded, invisible XSpan skeletons) — instead of the full 86.4 KB `codbi.general`. Because `{{CODBI_FULL_SECTION}}` (a per-element reference) excludes `codbi.general` entirely, the plain swap to the decision-only file would have been unsafe; the rethink variant guarantees the blind pass still has the build-syntax it needs. This saves ~56.7 KB (~14K tokens) per blind rethink call.
  - **Element structure reference** (`codbi-form-structure-rules.md`) was compressed from ~58.4 KB to ~37.5 KB.
  - All three new keys are registered in `prompts/index.json` and wired with a **fallback-safe chain** (`codbi.general_rethink → codbi.general_decision → codbi.general`) so existing databases that have not yet reseeded keep working, and the new keys auto-serve from the classpath on hot-deploy.
- **The legacy `AIFormAssistant` servlet is deprecated.** The frontend dispatches all AI requests to `CodBi_AICodBiAssistant`; `AIFormAssistant` (`CodBi_AIFormAssistant`) is kept only for backward compatibility with legacy callers and is now annotated `@Deprecated` with a KDoc note explaining it is superseded. It still works via the old servlet name for any external caller, so this is fully backward-compatible.

### Changed
- **Custom JavaScript is now attached to a FORM ELEMENT, never to the form**: the form-level `_customScript` marker and the `codbi-prop-custom-script` form property were REMOVED — `FormRenderCallback` no longer injects a form-wide `<script>` into the rendered form, `CodbiFormProperties.customScript` and the marker handling in `AIFormAssistant`/`AICodBiAssistant` are gone. A stale top-level `_customScript` in a model response is now explicitly IGNORED (`IGNORED_AI_MARKERS`) so it can never be persisted into the form JSON — covered by the new `FormLevelScriptIgnoredTest`. When a request asks for custom JavaScript (e.g. a JS calculator or a map→field sync), the AI writes it into an HTML-taking property of the element it belongs to (e.g. an XSpan's `rtevalue`), so the script is scoped to that element. Updated `formcycle.general`, `formcycle.widgets` (+ its compact variant), `codbi.form_structure_rules` and `codbi.form_short_task_instruction`; the workflow-mail prompts keep forbidding `<script>` because mail clients strip it.
- **The form/workflow AI assistants now have OPTIONAL internet access via Brave Search**: when `AI_BraveSearch_ApiKey` is configured, `Standard.performFormAssist` appends a web-access protocol to the conversation's system message and honours the model's `CALL:search(query='…')` / `CALL:fetch(url='…')` markers — it runs the Brave search (or fetches the page), feeds the result back as an extra assistant+user message and asks again for the normal output (max 2 rounds), then strips any leftover marker so a `CALL:` can never leak into the persisted form JSON. This lets the design-time AI look up CURRENT API documentation (e.g. a weather API's real endpoint and parameters) instead of inventing endpoints, and the form-element prompts now point it at the web-access tool before using any external URL. Without an API key nothing changes. A new plugin property **`AI_FormAssistant_WebAccess`** (default: enabled) switches web access OFF for these design-time assistant passes only — the runtime chat/QA keeps it. The element-placeholder reference now also states that `Net.URL` runs client-side inside the visitor's browser (a jQuery `$.get`, therefore CORS-bound) and returns the raw body — so a DWD/opendata URL can never work — and that weather / live-data widgets are to be built as self-contained JavaScript that fetches a VERIFIED CORS-enabled endpoint (`api.open-meteo.com`, `geocoding-api.open-meteo.com`, `api.brightsky.dev` for DWD data) — never an invented URL and never `opendata.dwd.de` / `api.dwd.de`. It also states that a follow-up targeting only ONE widget inside an element HTML content must change only that widget and re-emit every other part of the `rtevalue` byte-for-byte unchanged.
- **The AI no longer hand-writes JavaScript that fetches external data (it has no internet access)**: a "weather forecast" request made the model emit a `<script>` that `fetch()`es the invented, non-existent `https://api.dwd.de/weather/forecast/7day`, so the form could only ever show its "could not load" fallback (the run even looped asking the user for a "valid URL"). The custom-JavaScript rules now state that element JavaScript is for form-LOCAL behaviour only and MUST NOT fetch external data: for live data (weather, prices, news, addresses, opening hours, …) the AI uses the designated element placeholders — `{ AI.LLAMA.STD.QA > <question>; true;;;;;; }` (the `true` enables internet search at RUNTIME) via HTML.Text.Injector, or `{ Net.URL > <url> }` for a URL the user supplied — and never invents an API URL. Updated `formcycle.general` and the compact XSpan rule.
- **Interactive HTML an AI writes into a form element can no longer submit the form by accident**: with the new element-scoped JavaScript the model wrote a calculator as an XSpan `rtevalue` whose keys were bare `<button>` elements — a bare `<button>` defaults to `type='submit'`, so every key click sent the form (and its `DOMContentLoaded` wiring never ran, because the HTML is inserted into an already-parsed document). The prompts now require every `<button>` in such HTML to be `<button type='button'>` and the JavaScript to wire immediately (an IIFE, or one delegated listener on a stable `id`) instead of waiting for `DOMContentLoaded`. Updated `formcycle.general`, `formcycle.widgets` (+ its compact XSpan rule) and `codbi.form_short_task_instruction`.

### Fixed
- **Token counting completed for the last two paths that ignored it** — (1) the workflow MAIL and END-PAGE multilingualization passes (`runWorkflowMailMultilingualization`, `runEndPageMultilingualization` and its inert superseded twin) called `performFormAssist` six times without touching a token counter: each function now takes an `onUsage` callback, declares a small `reportUsage(messagesJson, response)` helper and reports every call (provider counters, estimate as fallback), and the two live call sites in `handleRun` pass the run's counting lambda (renamed `countClarificationUsage` → `countAssistUsage`, since it now serves every pass). (2) The STREAMING path (`ChatCompletionService.streamChatCompletion`, used by the runtime chat/QA) discarded the counters too: every SSE chunk is now checked with `extractUsage`, so llama.cpp's final-chunk `timings` (and any provider that streams `usage`) are reported through a new `onUsage` callback, and `Standard` accumulates them into the same per-thread accumulator (`takeLastAssistUsage()`), so a stream no longer vanishes from the accounting. Covered by a new test that feeds a chunk carrying `timings` and asserts the reported numbers.
- **The token counters no longer under-report — provider-reported usage plus the three previously invisible inference paths** — the logged token count was consistently lower than the real consumption for three reasons. (1) Every counted call was sized with `estimateTokens` = `text.length / 4`, which under-counts the JSON/HTML-heavy prompts of this plugin (roughly 3 chars per token), so even the counted calls were ~20-30% low. (2) `ChatCompletionService.chatCompletion` parsed ONLY `choices[0].message.content` and threw the server's own counters away: llama.cpp's `timings.prompt_n/predicted_n` and the OpenAI-compatible `usage.prompt_tokens/completion_tokens` are now read by the new `extractUsage` and reported through an optional `onUsage` callback. (3) Three whole inferences were missing from the total: the CLARIFICATION check (a full inference with its own ~300k-char system prompt, up to 5 rounds per run and one per user answer — `tryClarification` now reports its usage through an `onUsage` callback that `handleRun` adds to the counters), the WEB-ACCESS rounds inside `Standard.performFormAssist` (up to `maxWebAccessRoundTrips` extra completions, each re-sending the whole conversation — `Standard` now accumulates the provider usage of every round in a thread-local and exposes it via `takeLastAssistUsage()`, which the assistant prefers over the estimate; the accumulator is reset per call so it can never mix two passes), and the CHAT-CLASSIFICATION pass, which was counted only for pure chat turns, so every instruction run lost one entire inference. `estimateTokens` is kept strictly as the fallback for servers that report no usage, and its KDoc now says so.
- **YouTube/Vimeo embeds are written in the platform's EMBED FORM, and the AI no longer asks which element holds a widget or for a URL that already exists** — with a request describing a YouTube player-configuration error the run asked "Welche vorhandene Formelement enthält das Browser-Game …?" and "Bitte gib die genaue YouTube-Video-URL an" — although the element (an XSpan with the embed in its `rtevalue`) was in the form the build pass receives, and although the user had said the existing URL was already correct ("Die ist schon die richtige"); it then RE-ASKED "Wie heißt das vorhandene Video-Element?". Prompt fixes: `codbi.general` gained an EMBEDS section — a player error is about the EMBED FORM, not the URL, so YouTube must be `https://www.youtube.com/embed/<ID>` (ID taken from `watch?v=`, `youtu.be/`, `/shorts/`, `/live/` or an existing `/embed/`), Vimeo `https://player.vimeo.com/video/<ID>`, with the canonical `title`/`frameborder`/`allow`/`referrerpolicy`/`allowfullscreen` attributes, written into the EXISTING element's `rtevalue` and changing only the embed markup; `codbi.form_task_instruction` carries the compact version; and `codbi.clarification` now forbids asking WHICH element holds something the user describes (the build pass sees the whole form and finds it itself — the same FAIL as asking for a technicalId) and asking for a URL/media source the element already contains or that the user declares correct. Also `ClarificationQuestionFilter.normalizeQuestion` now strips a LEADING ENUMERATION: the popup hands an earlier round back as a numbered blob ("1. … 2. …") while the model re-asks a single one of those questions later, and without stripping the "1 " the two texts differed in their first character, so the duplicate guard let the re-ask through (covered by a new test case).
- **A URL that the AI looked up is no longer thrown away — and fixing an embed is now an ATTRIBUTE-LEVEL edit** — with "Die Einbettung leitet auf ein 404 aber du hast die richtige Seite mit Browser-Games gefunden. Du müsstet dort nur das Super Mario Game finden und die URL in die Einbettung die Du im Textelement erstellt hast benutzen statt der URL die jetzt drinnen ist." the run searched the web (Brave) and DID find the working page (`https://supermario-game.com/`) — but the lookup happened in the CLARIFICATION round, whose answer (`{"updateElement":…}` / `{"addElements":…}`) is not a question and is therefore DISCARDED; the build pass then only saw the unchanged form and re-emitted the OLD `https://www.retrogames.cc/nes-super-mario-bros.html` iframe `src`, so the 404 stayed. Two fixes: (1) `Standard.performFormAssist` now remembers every resolved web-search/fetch result of the CURRENT request in a thread-local (`takeWebAccessNotes()`), and `AICodBiAssistant` hands that transcript to the build pass as a `WEB RESULTS ALREADY LOOKED UP IN THIS RUN` system-prompt block with the instruction to write the matching URL into the EXISTING attribute — leftovers from an earlier request on the same pooled thread are drained when a run starts, so notes can only come from the run that consumes them (this also removes a misleading "All 0 clarification question(s) were already asked" log line for answers that carried no question at all); (2) the prompts now spell the edit out: `codbi.general` gained "Changing ONE VALUE inside an element's HTML = change ONLY that value" (keep the same element and every other byte of the `rtevalue`; change only the named attribute's value; never a new element, never a link instead of the embed, never the old URL, and use the direct page URL — not a listing page), `codbi.form_task_instruction` carries the compact version, and `codbi.clarification` forbids answering the clarification round with a form patch (`addElements`/`updateElement`/`items`) because it is discarded and silently loses whatever it contained.
- **A side-by-side layout with a full-width block below now really wraps — and live data is formatted in the form's language** — with "Die Vorteile und der Taschenrechner nebeneinander, die Wettervorhersage darunter und so breit wie das Textelement, die Daten im deutschen Format" the AI produced `#xi-spKIVorteileDesign{display:flex;gap:1rem}` plus `.weather{width:100%;flex-basis:100%}`: a WRAPPING flex container (`flex-wrap:wrap`) was missing, so the forecast could not move to its own line and all THREE blocks stayed in one row — twice, even after the request was repeated. The date was printed as the API's ISO string (`2026-09-21`) and the temperature breakdown used the raw numeric `weather_code` and a dot decimal separator. `formcycle.general` (CUSTOM JAVASCRIPT) now spells the CSS out: a block below a side-by-side row REQUIRES `display:flex; flex-wrap:wrap; gap:…` on the container, `flex:1 1 <pct>` (or a % width) on the side-by-side blocks and `flex:1 1 100%; width:100%` on the block below them, and the layout CSS belongs on a root `<div class='…'>` created inside the element's HTML property — never on the Formcycle element's own `#xi-<name>` wrapper. The same rule adds the FORMAT requirement (a requested "deutsches Format" is mandatory): dates via `toLocaleDateString('<lang>-<CC>')` (German form → `de-DE` → `21.9.2026`), numbers/temperatures via `toLocaleString('<lang>-<CC>')` (German → decimal comma), and NEVER a raw numeric `weather_code` shown to the user — it is mapped to text in the form's language (WMO code table given). The compact `codbi.form_short_task_instruction` carries the same two rules.
- **The AI no longer interrogates the user about details the form already contains (and stops asking after 3 rounds)** — with e.g. "Der Taschenrechner soll schöner aussehen … dazu eine 7-Tage-Wettervorhersage" on a form that ALREADY had that calculator and forecast inside one XSpan `rtevalue`, the run asked EIGHT rounds of questions (calculator type, where the result is shown, a Clear key and its label, read-only, 3×4 vs. linear layout, operator precedence, multi-digit input, whether to add a workflow node, client-side vs. workflow, plus place / number of days / icon source for the weather) — re-asking "Wie viele Tage sollen angezeigt werden?" and asking "Für welchen Ort …?" three times — before finally building. Prompt side (`codbi.clarification`): a new HARD RULE plus a numbered rule state that when the request only CHANGES an existing element, every detail that element already contains is GIVEN and must be read OUT OF THE EXISTING ITEM (never re-asked), that implementation trivia (labels, layout, evaluation order, read-only, workflow node vs. client-side JavaScript) must be DECIDED and answered NO_CLARIFICATION, and that a live-data widget must reuse the existing coordinates/day count (otherwise the visitor's own location and 7 days) instead of asking for them. Backend side, the new `ClarificationQuestionFilter` (`normalizeQuestion`, `isAlreadyAsked`, `dropAlreadyAsked`) enforces ONLY the prompt's own rule that a question must never be asked twice: every question whose text was already put to the user (verbatim or with the same 48-character stem, ignoring punctuation/non-breaking hyphens) is dropped, and when nothing new remains the run builds instead of opening the popup again. There is deliberately NO round cap — how much clarification is sensible is a prompt judgement ("take everything that already exists out of the existing item"), not a fixed count. Follow-ups from the same log: `codbi.form_task_instruction` now carries a hard "NEVER ASK IN THIS BUILD PASS" rule — pass 1 had answered `need_clarification` with "Bitte geben Sie die URL des DWD Wetter-API für die 7-Tage-Vorhersage (…) an" even though the clarification round had just returned `NO_CLARIFICATION` — and `formcycle.general` forbids mixing a CodBi functionality/element placeholder into such a JS widget (`data-cb-func`, `data-cb-replacement`, `[[INJECTOR_REPLACEMENT]]`, a `need_codbi_details` request for it). The forced detail rerun also received an EMPTY element list ("Pass-2 has 0 items to send "): the applicability report names its targets by element NAME (`spWeatherDay1`) while the lookup matched only `properties.id` (`xi-spWeatherDay1`), so nothing was selected and the model invented wiring — `AICodBiAssistant` and `AIFormAssistant` now match a target by id OR name and add the matched item itself to the expanded set. Covered by the new `ClarificationQuestionFilterTest`.
- **The form/workflow AI no longer invents a weather API URL (and no longer asks the user for one)** — with the prompt "… eine Wettervorhersage … für die nächsten sieben Tage … bezogen vom DWD." the run returned `need_clarification` — "Bitte geben Sie die URL des DWD Wetter-API für die 7-Tage-Vorhersage an (z. B. ein Endpunkt, der JSON-Daten für die nächsten sieben Tage liefert)." — asked the very SAME question again after the user answered "Suche selbst im Internet danach.", and finally wired the field with an INVENTED endpoint (`data-cb-replacement="{ Net.URL > https://example.com/dwd-forecast }"`). The custom-JavaScript rules already listed the verified CORS endpoints, but NOTHING forbade ASKING for one. Four prompt fixes: `codbi.clarification` gets a top-of-file HARD RULE plus a new MANDATORY-VALUES bullet stating that a weather/forecast/live-data endpoint is NEVER a value to ask about (the widget is self-contained JavaScript in the element's own HTML-taking property, e.g. the XSpan `rtevalue`, against the VERIFIED CORS-enabled endpoints — Open-Meteo forecast + geocoding, Bright Sky for DWD data — so the run must end in NO_CLARIFICATION), that "DWD-Daten" means Bright Sky and never a `opendata.dwd.de` / `api.dwd.de` file-server URL, and that a `Net.URL` value such as `https://example.com/dwd-forecast` is an invented URL (a FAIL); the already-existing "treat a delegated answer as ANSWERED, never ask it again" rule now also names "Suche selbst im Internet danach", "recherchiere selbst", "look it up yourself", "search the internet for it" and "google it"; `codbi.element_placeholders` (the Net.URL section) forbids wiring `Net.URL` for weather/live data and forbids asking the user for an API URL at all, and repeats the three verified endpoints; `formcycle.general` (CUSTOM JAVASCRIPT) now states that a clarification question asking for a weather/live-data API URL is a FAIL because the verified endpoints listed there are ALWAYS the answer; and `codbi.form_short_task_instruction` repeats the rule for the no-questions path.
- **Workflow node/trigger detection no longer fails (every workflow element was treated as "not installed")**: `InstalledFormcycleElements.invokeGetAllKnown` invoked `WorkflowRegistry.Node/Trigger.getAllKnown(...)` without lifting the language-level access check, so on modern JDKs it failed with `IllegalAccessException: … cannot access a member of class de.xima.fc.plugin.workflow.registry.WorkflowRegistry$AWorkflowElementRegistry with modifiers "public final"` (the method is declared by that NON-PUBLIC base class). The snapshot then reported `0 node(s), 0 trigger(s)`, and with "Nicht installierte Elemente erstellen" active NO workflow node or trigger was ever transmitted to the AI. Both reflective calls now call `trySetAccessible()` before invoking.
- **A requested "animierte SVG Illustration" now comes out as a designed scene instead of a placeholder drawing**: with "… Noch im Text aber über der ersten Zeile soll eine animierte SVG Illustration sein die ein Formular das durch eine KI aufgewertet wird zeigt." the model emitted a single grey `<rect>` + `<text>Formular</text>` + a green circle labelled "AI" — a wireframe-level placeholder. Cause: the prompt only required that an ANIMATED inline SVG EXIST (mechanism: SVG SMIL / in-`rtevalue` `@keyframes`, self-contained, no remote image), and said nothing about the drawing's QUALITY, so the model produced the smallest markup that satisfies the rule. The rules now demand a real ILLUSTRATION: a canvas whose `viewBox`/aspect ratio is DERIVED from the text's width and placement (wide banner for a full-width text, compact for a narrow column/inline, responsive `width='100%'`), SEVERAL layered `<g>` groups, a palette taken from the text's own colours/cards, `<defs>` with `<linearGradient>`/`<radialGradient>` fills plus an optional `<feDropShadow>`, rounded rects/paths for the objects (a form/browser card with a title bar and three window dots, form rows as rounded rects, an accent "AI" chip, sparkle shapes) and a soft background shape — with an explicit FAIL for one plain grey `<rect>`, a bare shape, or WORDS standing in for the artwork (a box labelled "Formular", a circle labelled "AI"), and 2-4 meaningful details (sparkles pulsing, rows fading in, a moving highlight) must actually animate. The rules additionally require SINGLE quotes for EVERY SVG/HTML attribute value inside the `rtevalue` — the observed output used ESCAPED double quotes (`width=\"200\"`), which produces a broken attribute so the SVG can render at the wrong size or not at all. A second follow-up fixed the two defects the NEXT output revealed: (1) SVG NAMES ARE CASE-SENSITIVE and the model wrote `viewbox`, `animatetransform`, `attributename` and `repeatcount` — all of which the browser IGNORES, so the canvas was discarded (the drawing misplaced) and NOTHING animated. `AICodBiAssistant` now repairs that deterministically in `normalizeSvgAttributeNames`, which is POSITION-AWARE: ELEMENT names (every camelCase SVG/SMIL element — `linearGradient`, `radialGradient`, `clipPath`, `foreignObject`, `textPath`, `animateTransform`, `animateMotion`, `feFuncA`…`feFuncR`, `feGaussianBlur`, `feDropShadow`, `feMergeNode`, …) are rewritten only right after `<` and before whitespace/`>`/`/`, and ATTRIBUTE names (the camelCase ones such as `viewBox`, `attributeName`, `repeatCount`, `gradientUnits`, `stdDeviation`, `clipPathUnits`, `preserveAlpha`, … PLUS the hyphen-omission variants `strokewidth` → `stroke-width`, `stopcolor` → `stop-color`, `fillopacity` → `fill-opacity`, `fontsize` → `font-size`, `textanchor` → `text-anchor`, …) only after whitespace and before `=`. A word that merely OCCURS in the visible text is therefore never touched, and an unknown/invented name is left as-is — the two registries are the COMPLETE SVG/SMIL name sets — 39 camelCase ELEMENTS (incl. the deprecated `animateColor`/`altGlyph`/`altGlyphDef`/`altGlyphItem`/`glyphRef`/`hKern`/`vKern`) and 111 non-lowercase ATTRIBUTES — with the lookup key derived by dropping the hyphens, so `strokewidth`/`stopcolor`/`fontsize`/`textanchor` resolve to the same canonical entry as the correct spelling; CLOSING tags (`</fegaussianblur>`) are repaired as well, and the map is built from the canonical lists via `associateBy`, so no misspelling list has to be maintained by hand. Only a name outside the standard stays as-is, so the prompt rules remain the primary mechanism and the prompts name the exact spellings (`viewBox`, `preserveAspectRatio`, `attributeName`, `repeatCount`, `animateTransform`, `linearGradient`, `stop-color`, `stroke-dashoffset`) with a naming/quoting example; (2) composition & animation quality — the rules now require a RECOGNISABLE scene (form/browser card with title bar + three window dots + 3-4 field rows, an accent "AI" chip/sparkles, a soft backdrop, gradients on the main shapes, a 4-6 colour palette; one rectangle plus one circle/line or dashed connector curves as the main visual is a FAIL) and only VISIBLE animations (rotating a plain `<circle>` changes nothing: rotate/scale a multi-shape group, use `stroke-dashoffset` on a path, `opacity` on rows or `animateTransform` scale on a badge). Covered by the new `lowercased SVG names are repaired to their camelCase spelling` case in `DuplicateTextSpanGuardTest` (9 cases, all green — including an empty span being dropped, a runtime-wired span being kept, a merely re-styled duplicate being dropped, and the SVG name repairs with a negative case proving a word that only OCCURS in the visible text is untouched). Updated `formcycle.widgets` (`formcycle-widgets.md` XSpan section + its compact variant) and `codbi.form-structure-rules`. A THIRD follow-up covered the CSS side of the same question: CSS PROPERTY/at-rule/keyword names are case-INSENSITIVE (a wrongly-cased `Stroke-Width` still works), so no repair is needed there — but every CSS IDENTIFIER is case-SENSITIVE and author-chosen, so it cannot be auto-normalised (renaming a custom property or a theme class could break references outside the `rtevalue`). The rules now require the identifiers to MATCH: each `@keyframes` name referenced IDENTICALLY by an `animation`/`animation-name` (an undefined name silently disables the animation, an unused `@keyframes` is dead code — the observed `@keyframes rotateGlobe` defined while no rule used it), each selector class identical to the `class='…'` in the markup, and each `url(#id)`/`href='#id'` identical to the referenced `id`. A FOURTH follow-up addressed the remaining quality gap: abstract quality adjectives turned out to be weak, so the XSpan reference now carries a complete WORKED EXAMPLE SVG (gradient backdrop + soft ground shadow, window card with title bar and three dots, 4 labelled field rows fading in staggered, an AI chip with a sparkle cluster, dashed connectors drawing themselves, `prefers-reduced-motion` handling) with the explicit statement that a return to a bare grey rectangle plus a circle/line is a REGRESSION — plus the pitfall that a CSS `transform` animation on an element which also carries a `transform` ATTRIBUTE REPLACES that attribute (the shape jumps to the origin), so the positioning belongs on an outer `<g transform='…'>` and the animated class on an inner `<g>`. The example is deliberately framed as ADAPT-DON'T-COPY: it is a STRUCTURE template (backdrop + ground shadow → layered groups → the topic's main object built from primitives → accent element → sparkle cluster → self-drawing connectors → staggered entrances → reduced-motion) whose SUBJECT must be replaced by whatever the request describes (map → map panel with roads/pins, authority → building with a portico, documents → stacked pages with a seal, person → a figure plus an ID card), with palette/`viewBox`/text language taken from the context; and because every `rtevalue` is rendered into the SAME document, all `id`s and classes must be UNIQUE PER ELEMENT (a duplicated `id` makes `url(#…)`/filter references and class rules bind to the FIRST match). Updated `formcycle.widgets` (`formcycle-widgets.md` XSpan section + its compact variant) and `codbi.form-structure-rules`. A FIFTH follow-up closed two remaining holes. First, the repair had only been wired into the unified `AICodBiAssistant`: a run through the simpler `AIFormAssistant` still published the lowercased `viewbox` / `preserveaspectratio` / `radialgradient` names, so the repair is now extracted into the shared `SvgNameRepair` object (`repairXSpanRtevalues`), called from `AIFormAssistant.handleRun` on the FINAL form after the field restore, and covered by the new `SvgNameRepairTest` (9 cases: camelCase restore, SMIL names, hyphen-omitted attributes, filter and clip elements, deprecated elements, prose that merely mentions a name staying untouched, byte-identical passthrough, a form without any XSpan and invalid JSON). Second, the prompt rules now forbid NO-OP animations - a rotation or a `scaleY` on a plain circle changes nothing visible, so a rotation only reads on an ASYMMETRIC shape (a face, dial, star or logo), and `transform-origin` needs `transform-box:fill-box` or the shape DRIFTS towards the viewport origin - and require the drawing to SHOW THE RELATIONSHIP the request names: for a form that is supposed to be upgraded by an AI, the scene must contain form UI (labelled field rows plus a submit button) with the AI contribution VISIBLY attached to it (a suggestion chip on ONE field plus an arrow into the form), so a blank rectangle next to a circle and a globe with dashed arcs is a FAIL. Updated `formcycle.widgets` (`formcycle-widgets.md` XSpan section + its compact variant) and `codbi.form-structure-rules`.   requests to add the translations as Formcycle's per-language element map
  (`properties.i18n[<lang>][<prop>]`, plus the per-option / per-button `i18n` for XSelect options and
  XButtonList buttons) while leaving every base/default-language text unchanged — mirroring what the
  designer does when the Form language selector is set to that language. The prompts
  (`codbi.form_structure_rules` / `codbi-form-structure-rules.md` and `formcycle.general` /
  `formcycle-general.md`) now document the storage format, and both form assistants
  (`AICodBiAssistant.kt`, `AIFormAssistant.kt`) no longer discard the AI-emitted `i18n`: a new
  `mergeItemI18n` restore step merges it with the original item translations so already-translated
  languages are preserved when a second language is added.
- **Compact single-line AI JSON in the logs**: every server-side log of the raw AI form/workflow
  response (including the "AI returned invalid JSON / unparseable response" warning, which printed the
  whole pretty-printed payload over dozens of lines) is now emitted as one compact line via a shared
  `compactJsonForLog` helper (shared `AiJsonLogging.kt`, replacing per-class copies) so the logging
  window shows the complete payload without line-wrapping scroll noise — plus the character count so a
  truncated (over-length) response is immediately recognizable. The whole-form-translation prompts also
  instruct the AI to emit compact JSON and never empty `"i18n": {}` maps, keeping large-form outputs
  within the model's length limit.
- **Multilingual workflow mails on whole-form translation (`FC_SWITCH` on `[%lang%]`)**: when the form
  AI translates a whole form into ADDITIONAL languages, it now also emits a structured, language-
  agnostic marker (`"_workflowMailLanguages": ["<baseCode>", "<addedCode>", ...]`, base language
  first — same model-declared-signal pattern as `_codbiApplicability`, never a server-side keyword
  guess). When the marker is present and a workflow version is available, `AICodBiAssistant` runs a
  dedicated multilingualize pass (`runWorkflowMailMultilingualization`, prompt
  `codbi.workflow_translate_instruction` / `codbi-workflow-translate-instruction.md`): the AI names the
  existing **consumer-facing** `FC_EMAIL`/`FC_DOI_INIT` nodes (recipient = a `[%…%]` consumer email
  field or a DOI invitation; internal/admin/error mails are skipped) and provides the subject/body
  translation per added language. The backend then wraps each chosen node **in place** into an
  `FC_SWITCH` with `switchValue="[%lang%]"` (Formcycle's native placeholder for the language the form
  was filled out in — verified in the official howto
  `help8.formcycle.eu/…/103000047241-internationalisierung-im-workflow` and against
  `FcSwitchExecutor`, which resolves the switch value through the condition operand mapper). The
  original mail stays byte-for-byte on the base-language `FC_SWITCH_CASE` and the
  `FC_SWITCH_DEFAULT`; every other language gets a clone with translated subject/body/senderName while
  `to`/`from`/attachments/DOI pages and all placeholders are preserved. The switch keeps the mail's
  position, so the lane's continuation after it is untouched — no new lane/trigger/endpoint is created,
  and no submit button or field is added. The marker is stripped from the form before it is saved.
  Prompt rules were added to both form prompts (`codbi.form_structure_rules`,
  `formcycle.general`) and registered in `index.json`; covered by the FS12 scenario in the whole-form
  test-prompts plan.
  The assistant dialog (`ai-assistant.ts`) now also sends `workflowVersionId` on **form-only** runs
  when a workflow exists (previously workflow/both only), so the translation run reaches the
  multilingualize pass; the existing "formJson + workflowMessage" response handling then publishes the
  translated form and reloads the designer to show the new switch.
  The multilingualize pass feeds the model only a **condensed candidate list of the FC_EMAIL /
  FC_DOI_INIT nodes** (id, name, type, params) plus an explicit output rule instead of the whole
  workflow tree (feeding the full tree made the model echo the workflow back instead of answering the
  small mails payload, so no switch was created), and **retries once with a strict schema instruction**
  when the reply contains no usable `targetNodeId`+`translations` entry — the form translation itself
  is never failed when this optional pass yields nothing. The candidate collector descends through
  both `children` and the task-level `rootNode` of the workflow-structure JSON (the node tree lives
  under `rootNode`; without that descent it found zero mail nodes and skipped the wrap — observed
  "no FC_EMAIL/FC_DOI_INIT node found - nothing to wrap").
  **Which mails are consumer-facing is the AI's own decision** — no server-side filter is applied (a
  deterministic filter can never cover every way a mail is destined to the consumer or an internal
  office). The model must therefore return an explicit `toConsumer` boolean for **EVERY** candidate
  node in a single pass (verdict + translations together): the runner validates that no candidate is
  missing a verdict and **retries once with a strict schema instruction** (listing the missed ids)
  when any candidate lacks a verdict or the reply is unusable; it then wraps ONLY the nodes the model
  itself marked `toConsumer: true` and leaves internal/back-office/error mails untouched. Live
  validation had shown the model wrapping almost every mail node (including "Benachrichtigung für die
  Sachbearbeitung" and "E-Mail an Kasse"); the workflow-translate prompt now gives intent-based
  guidance (who reads the mail and what it is for) instead of relying on recipient strings or keyword
  lists.
- **Whole-form translations never trigger the CodBi "blind" re-evaluation pass**: both form
  assistants (`AICodBiAssistant`, `AIFormAssistant`) now skip that second pass (which re-sends the
  whole large form and can exceed the model's output limit → "AI returned invalid JSON") whenever the
  form-AI response declares the structured `_workflowMailLanguages` translation marker — even when the
  model omitted `_codbiApplicability` entirely. A whole-form translation only ADDS per-language text
  fields and never a CodBi element, so the blind CodBi re-evaluation is pointless and harmful for it.
  The form-AI prompt reminder also now asks the model to emit `_workflowMailLanguages` (base language
  first) plus `_codbiApplicability.codbiVerdict = "none"` on every whole-form translation.
- **Later language additions EXTEND an already-multilingual mail `FC_SWITCH` instead of wrapping it
  again**: when the whole form is translated into languages that a previously created `[%lang%]` mail
  switch does not cover yet (e.g. "Übersetze das Formular ins Englische und Französische." on a form
  whose de/it `FC_SWITCH` was built by an earlier run), the mail pass no longer leaves English/French
  consumers on the German default mail. The candidate collector now feeds the AI two kinds of
  candidates — `"MAIL"` (a plain `FC_EMAIL`/`FC_DOI_INIT` to wrap) and `"SWITCH"` (an existing
  `[%lang%]` `FC_SWITCH` already carrying translated mail clones, reported with its
  `existingCaseLanguages`, `defaultBranchId` and the first clone's type/name/params) — and it does not
  descend into a handled `[%lang%]` mail switch's subtree, so clones are extended, never re-wrapped.
  The model is told to translate a SWITCH only into the form languages missing from its
  `existingCaseLanguages`. The apply loop dispatches per kind: a SWITCH candidate goes to the new
  `extendMailSwitchNode`, which appends one `FC_SWITCH_CASE` (+ `SEQUENCE` + translated mail clone
  named "<switch name> (<lang>)") per added language under the SAME switch; the `FC_SWITCH_DEFAULT`
  stays at index 0 (the FIRST child — Formcycle requires the default as the first branch or the
  switch is INVALID) via `ensureSwitchDefaultFirst`, which also heals switches that were generated
  with the default placed last. Verified against the de/it form: a follow-up
  de→en+fr run now yields `Extended existing FC_SWITCH … with new language case(s): en, fr` with the
  en/fr branches inserted before the default.
- **Multilingual Abschlussseiten (ending pages) by REUSE — never created**: the ending-page pass that
  was parked (server-side creation of TEMPLATE_CLIENT rows is impossible from the plugin: no JPA
  entity, encrypted `TEXTVALUE`, no creation API) is now active in a reuse-only form. When a whole-form
  translation adds languages, `AICodBiAssistant` additionally wraps every consumer `FC_SHOW_TEMPLATE`
  (Abschlussseite) node into an `[%lang%]` `FC_SWITCH` (same trigger/marker and same verdict-only
  single-pass + strict-retry pattern as the mail pass: the model returns a `toConsumer` verdict per
  condensed candidate, never the whole tree). Each non-base case points at the **already existing**
  localized page whose NAME is `<base> _CB_<LANG>` (e.g. `Formular versendet _CB_EN`; `de-CH` →
  `_CB_DE-CH`) — resolved deterministically by the backend from the client's `TEMPLATE_CLIENT` rows
  (NAME + UUID are plain text; the encrypted content is never read) via the new
  `listClientTemplates` / `findLocalizedTemplate`. When no localization exists the case falls back to
  the **original** page — a page is never created, invented or edited. An already-`[%lang%]`-wrapped
  ending-page switch is EXTENDED with the missing languages (new `extendEndPageSwitchNode`, mirror of
  `extendMailSwitchNode`), never double-wrapped. `handleRun` runs the ending-page pass right after the
  mail pass (both under the same `_workflowMailLanguages` gate + `workflowVersionId`) and emits one
  combined `workflowMessage`. The obsolete page-creation helpers
  (`ensureEndPageForLanguage`, `setTemplateText`, `setNewUuid`, `readTemplatePage`, …) are marked
  SUPERSEDED/inert.
- **Multi-language whole-form translations run ONE LANGUAGE PER AI PASS (sequential)**: when a request
  asks to translate the whole form into two or more NEW languages at once ("translate to English and
  French"), the backend no longer lets a single AI response carry every translation — that oversized
  output truncated mid-JSON on large forms (observed live at 15587 chars) and aborted the run before
  the workflow passes. The new `planWholeFormTranslation` (model-declared languages, reached via a
  cheap fallback-safe hint — the AI decides, never keyword parsing) detects the multi-language case;
  `runSequentialWholeFormTranslation` then reuses the proven single-language form pipeline
  (`runFormModification`) once per language on the ORIGINAL persist, each pass restricted to its one
  language, and merges the per-language i18n (labels/headers/legends/rtevalues plus nested
  per-option/per-button i18n) into a single final form via `overlayLanguageI18n`. `handleRun` engages
  this only when ≥2 new languages are planned (otherwise the normal single pass is unchanged), and it
  overrides the `_workflowMailLanguages` list to the full base-first set so the ONE combined mail +
  ending-page multilingualization runs afterwards for all languages.
- **`FC_SWITCH` children obey Formcycle's required layout — default branch at index 0**: a switch node
  is INVALID in Formcycle unless its `FC_SWITCH_DEFAULT` branch is the FIRST child
  (parent_order_idx 0); the language `FC_SWITCH_CASE`s follow it. All multilingualize builders now
  create the default branch first (mails + ending pages), the extenders no longer move the default to
  the end, and the new `ensureSwitchDefaultFirst` reorders any switch whose default is not the first
  child — so a re-run of the same translation request also heals switches that earlier runs generated
  with the default last (observed live: ending-page switch had case(0), case(1), case(2), default(3)
  and the extended mail switch had its default forced to index 5). The workflow-AI switch builder
  already followed this convention.
- **Repeat whole-form translations are form no-ops (no more invalid-JSON aborts)**: when the request is
  a whole-form translation but EVERY named language is already present on the already-multilingual form
  (e.g. re-running "Übersetze das Formular ins Englische und Französische." after en+fr were added), the
  backend no longer re-runs the generic full form-rebuild pass — that pass re-emitted the whole
  multilingual form, exceeded the output budget and returned truncated, single-quoted invalid JSON
  (observed live at 17366 chars), aborting the run before the workflow passes. The translation-plan AI
  now reports `translationRequest=true` even for such repeat requests (with `addLanguages=[]`), and
  `handleRun` then leaves the form unchanged and still runs the workflow multilingualize (mails +
  ending pages), which verifies coverage and heals `FC_SWITCH` ordering.

### Fixed
- **Sensitive-element detection missed functionality names**: `AiAssistantLog.usedSensitiveElements`
  only scanned the **value** of each attribute, so a functionality used via `data-cb-func` (e.g.
  `Sys.Log.Console`, whose name lives in the attribute `name` with an empty value) never matched a
  configured sensitive element. Detection now also scans the attribute `name`/`kind` and the nested
  `data-cb-*` parameters, so funcs, EPs and their payloads are all detected.
- **Form widgets silently dropped when the AI requests details twice**: if the AI answered the
  initial pass with `need_codbi_details` and the detail-rerun again answered `need_codbi_details`
  (e.g. a small model first asking for CodBi details, then for specific widget types), the second
  details request was spliced into the form as-is — no `items` — so every requested widget was lost.
  `rerunWithCodbiDetails` now detects a second `need_codbi_details` and reruns (bounded by
  `MAX_FORM_RERUNS`) with the newly requested elements/widgets, so the widgets the user asked for are
  not silently dropped.
- **Sensitive-element auto-open after workflow creation**: when the AI assistant also creates a
  workflow, the designer reloads the page to store it. The change-log component was only mounted on
  demand, so after the reload its `ngOnInit` never ran and the pending sensitive-element highlight
  persisted in sessionStorage was never consumed — no popup appeared. The fix: `cb-ai-assistant-log`
  is now mounted on every designer page load, the sensitive elements are written to sessionStorage
  inside `doReload()`/the workflow-only reload path (immediately before `window.location.reload()`,
  the same pattern as the standards write, so no intermediate async rendering can consume them), and
  the always-mounted assistant element reopens the change log after the reload as a fallback — briefly
  waiting for the designer to report the current form key so the log is scoped to the just-reloaded
  form.
- **Change-log author resolution**: the inference author was resolved via `params.benutzer?.loginName`,
  which is empty in the plugin servlet-action context, so no user was recorded/displayed (the top-level
  author badge was empty and the sensitive-check badge read "checked by ?"). `currentUsername` now uses
  `params.user.userName` — the same accessor as the Local API Doc store, which reliably resolves the
  logged-in user (e.g. `sadmin`).
- **Change-log auto-open after reload made robust**: besides the sessionStorage/localStorage handoff,
  the change log now also queries the database on every designer page load: the newest entry of the
  current form is examined and, if it used sensitive elements within the last few minutes and not all
  of them are acknowledged, the dialog auto-opens with those elements highlighted. `loadLogs` returns a
  per-entry `sensitiveUsed` list (recomputed from the stored form changes against the current
  `AI_Log_SensitiveElements`) so the check is driven by DB state rather than by fragile frontend
  timing. A plain-JS poller in `enableAICodBiAssistantDialog` (runs on every designer page load)
  additionally keeps dispatching the `codbi:ai-assistant-log:open` event while a pending sensitive
  list exists and independently queries the newest log entry — covering any case where the Angular
  component's `ngOnInit` timing is missed after the reload.
- **Sensitive-check persistence failed**: ticking a sensitive node's dismiss checkbox logged
  `org.hibernate.InstantiationException: No default constructor for entity ...
  CodbiAiLogSensitiveCheck`, so the check was never stored. The entity's constructor parameters now
  all have defaults, which makes Kotlin emit the public no-arg constructor JPA requires.

### Changed
- **Sys.Log.Console prompt behavior**: when the prompt asks to log something to the browser console,
