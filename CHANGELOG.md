## [Unreleased]

### Added
- **`<[...]>` field references are now a CodBi-wide parameter feature instead of an `AI.LLAMA.STANDARD.TXTVERIFY` special case.** Every `data-cb-*` parameter — and every Element-Placeholder parameter — resolves `<[this]>`, `<[.FieldName]>` / `<[#id]>` / any CSS selector, and bare `<[FieldName]>` (CSS class → `data-name` → plain selector) before the functionality is invoked. Resolution is scoped to the nearest ancestor `.XContainer` / `.XFieldSet` of the referencing element with document fallback, controls contribute their live `value`, and wrapper elements delegate to their first contained control ([`resolveFieldPlaceholders()`](src/main/web/packages/form/src/js/global-scope.ts:1448), [`resolveFieldReference()`](src/main/web/packages/form/src/js/global-scope.ts:1405)). `<[...]>` and Formcycle's `[%field%]` placeholders are resolved in ONE pass so a substituted value cannot smuggle in another placeholder ([`resolveParameterPlaceholders()`](src/main/web/packages/form/src/js/global-scope.ts:1472)); unresolved references stay literal, `<[this]>` is kept while the field is empty, `°<[` escapes a literal token, and commas inside `<[...]>` no longer split a `data-cb-*` value into a CSV array ([`parseAttributeValue()`](src/main/web/packages/form/src/js/global-scope.ts:2362)). Because resolution is initialization-time, functionalities that need live values keep working: they read the untouched raw attributes, and `AI.OCR` now resolves its patterns from the raw `data-cb-pattern` / `data-cb-pattern_*` attributes instead of the already resolved `toLoad` values ([`ai.ocr.ts`](src/main/web/packages/form/src/js/Functionalities/ai.ocr.ts:129)). Documented in the [README](README.md:173), in the AI prompt rules ([`codbi-functionalities.md`](src/main/resources/com/github/xima_formcycle_entwicklerkreis/fc/plugin/codbi/prompts/codbi-functionalities.md:13)) and covered by 17 new tests in [`global-scope.spec.ts`](src/main/web/packages/form/__tests__/global-scope.spec.ts:104).

- **`<[...]>` references can now read a PROPERTY or JSON path of the referenced field, not only its value — `<[tfJson.total]>`, `<[tfJson::items[0].name]>`, `<[this::innerHTML]>`.** The reference grammar is parsed by [`parseFieldReference()`](src/main/web/packages/form/src/js/global-scope.ts:1122): `<[Base::path]>` is the explicit form (works with `this`, any bare name and any CSS selector), while the dot shorthand `<[FieldName.path]>` only applies to a bare name so existing selector references like `<[.tfName]>` keep their meaning (use `<[.tfJson::items[0].name]>` there). A field value that parses as JSON is traversed FIRST ([`walkFieldPath()`](src/main/web/packages/form/src/js/global-scope.ts:1276)); otherwise the path is read as a whitelisted DOM property or `dataset` entry ([`walkDomFieldPath()`](src/main/web/packages/form/src/js/global-scope.ts:1318)) — `innerHTML`, `outerHTML`, `textContent`, `innerText`, `value`, `checked`, `className`, `id`, `name`, `type`, `title`, `placeholder`, `href`, `src`, `disabled`, `readOnly`, `hidden`, `maxLength`, `rows`, `cols`, `multiple`, `selectedIndex`, `tagName`. Objects/arrays are serialized as JSON, unknown paths and `<[this]>`-on-empty keep the literal token, and only OWN properties are read, so `__proto__`/`prototype`/`constructor` can never be reached. Path tokens may contain `]` (e.g. `items[0]`) because the token now ends at `]>` rather than at the first `]`. Documented in the [README](README.md:173) and the AI prompt rule, covered by 5 new path tests in [`global-scope.spec.ts`](src/main/web/packages/form/__tests__/global-scope.spec.ts:183).

### Changed
- **A mail that must list ALL rows of a repeatable container is now built as `FC_FOR_EACH_LOOP` + server-attribute accumulation + ONE `FC_EMAIL`, instead of a single mail with a bare row placeholder.** Reported case: "Beim Klick auf Senden sollen alle eingegebenen Vor- und Nachnamen als Auflistung in einer Mail an A@B.C mit dem Betreff Anmeldungen gehen" produced one `FC_EMAIL` whose body was `<li>[%tf3%] [%tf4%]</li>` — only the FIRST row of the repeatable container, with the list lost. The always-sent repeatable-container section of [`codbi-workflow-task-instruction.md`](src/main/resources/com/github/xima_formcycle_entwicklerkreis/fc/plugin/codbi/prompts/codbi-workflow-task-instruction.md:39) gained a LANGUAGE-AGNOSTIC `LIST / ROSTER OF ALL ROWS` rule: plural/ALL phrasing ("alle eingegebenen Vor- und Nachnamen als Auflistung", "all entered first and last names as a list", "die Liste aller …", "jede Anmeldung", "per row") means ONE `FC_FOR_EACH_LOOP` (`FORM_FIELD_REPETITIONS`) that APPENDS one readable `<li>`/line per row to a server attribute (`[%$RECORD_ATTR.<key>%]`), followed by ONE `FC_EMAIL` referencing it (seed the opening markup before the loop, close it after); one mail PER row instead puts the `FC_EMAIL` INSIDE the loop. A bare row placeholder in the mail body is explicitly WRONG, and an EMPTY/INCOMPLETE container field list no longer causes a fallback: the requested row fields (technical IDs from the FORM ELEMENTS list) are treated as that container's children and iterated. The detailed reference gained the matching `COLLECT-ROWS-TO-MAIL-LIST` pattern with the reported first/last-name example ([`formcycle-workflow-nodes.md`](src/main/resources/com/github/xima_formcycle_entwicklerkreis/fc/plugin/codbi/prompts/formcycle-workflow-nodes.md:798)), the pass-1 compact FIRST lines now advertise the loop for repeatable rows and warn inside the `FC_EMAIL` entry ([`formcycle-workflow-nodes-compact.md`](src/main/resources/com/github/xima_formcycle_entwicklerkreis/fc/plugin/codbi/formcycle-workflow-nodes-compact.md:111)), and [`buildRepeatableContainersContext()`](src/main/kotlin/com/github/xima_formcycle_entwicklerkreis/fc/plugin/codbi/logic/cb/AICodBiAssistant.kt:11263) now collects a container's fields RECURSIVELY (nested child containers) and flags an unresolved container explicitly (`<none resolved — …>`). Guarded by the new [`WorkflowRepeatableListPromptTest`](src/test/kotlin/com/github/xima_formcycle_entwicklerkreis/fc/plugin/codbi/logic/cb/WorkflowRepeatableListPromptTest.kt:1). Re-seed the prompts (`AI_FormAssistant_Prompt_Reseed=true`).
- **The workflow AI now builds ONE `FC_SWITCH` when a request describes a multi-case decision over the SAME field, and falls back to `FC_MULTIPLE_CONDITION` (if-nodes) only for a single yes/no condition.** Reported case: "wenn in Popel 'Haus' steht eine Mail …, wenn dort aber 'AST' steht, die hochgeladene Datei herunterladen" produced TWO nested `FC_MULTIPLE_CONDITION` nodes, although a switch/case node is the logical construct (the backend already creates `FC_SWITCH` + `FC_SWITCH_DEFAULT`/`FC_SWITCH_CASE` from `_cases`/`_defaultChildNodes`). The always-sent build instruction [`codbi-workflow-task-instruction.md`](src/main/resources/com/github/xima_formcycle_entwicklerkreis/fc/plugin/codbi/prompts/codbi-workflow-task-instruction.md:307) gained a LANGUAGE-AGNOSTIC rule that decides by MEANING (never by keywords) between the two shapes: (a) SEVERAL distinct states/values of the same field, each leading to its OWN different action(s) → ONE `FC_SWITCH` with `switchValue` and one `_cases` entry per action set (several values for the same actions share one `caseValues` array), plus `_defaultChildNodes` only when a default action is requested; (b) a single yes/no check, checks on different fields, an empty/not-empty check, or several values leading to the SAME action → `FC_MULTIPLE_CONDITION`. Emulating a switch with if-nodes is explicitly FORBIDDEN (an `_elseChildNodes` branch that tests the same field again, a chain where each NO branch opens the next condition, or one condition per value as sibling lanes). The existing if/else rule was scoped to ONE single yes/no condition and points multi-case decisions to the new rule. The pass-1 compact catalogue ([`formcycle-workflow-nodes-compact.md`](src/main/resources/com/github/xima_formcycle_entwicklerkreis/fc/plugin/codbi/formcycle-workflow-nodes-compact.md:319), whose FIRST line is the only text pass-1 sees) now advertises `FC_SWITCH` as the multi-branch choice and makes `FC_MULTIPLE_CONDITION` point a multi-case decision to it, and the detailed reference ([`formcycle-workflow-nodes.md`](src/main/resources/com/github/xima_formcycle_entwicklerkreis/fc/plugin/codbi/prompts/formcycle-workflow-nodes.md:707)) documents the anti-pattern in both node sections plus the reported Haus/AST example as one `FC_SWITCH`. Guarded by the new [`WorkflowSwitchVsConditionPromptTest`](src/test/kotlin/com/github/xima_formcycle_entwicklerkreis/fc/plugin/codbi/logic/cb/WorkflowSwitchVsConditionPromptTest.kt:1). Re-seed the prompts (`AI_FormAssistant_Prompt_Reseed=true`).

While the question is OPEN its SIDE EFFECTS are deferred: [`setElementCssClass()`](src/main/web/packages/designer/src/js/CodbiElementMarkers.ts:1241) gained a `deferNotify` option that suppresses the persist-differ nudge (which syncs the draft and thus makes FORMCYCLE re-render the element preview) and the debounced badge/preview refresh, and the new [`flushElementCssClassChange()`](src/main/web/packages/designer/src/js/CodbiElementMarkers.ts:1282) runs them exactly ONCE when the question is answered - also on cancel - INCLUDING the re-push into the designer's own `cssclasses` editor, whose `setValue` fires the property callback and was the second trigger of that re-render. On top of that, `suspendElementPreviews()` / `resumeElementPreviews()` (CodbiElementMarkers) FREEZE every element preview while the question is open: `applyElementPreview` does not (re)build or tear down a preview, a pending debounced re-apply is dropped (the resume re-derives it) and the 500 ms fit loop - which dispatches `resize` and thereby makes FORMCYCLE re-measure its cells - postpones its steps. `renderServerPreview` additionally drops the height pin left over from the PREVIOUS preview before it reloads, so a re-applied preview can no longer be clipped by a stale `minHeight` (that was why the FIRST re-render looked fine while every following one came back clipped and with FORMCYCLE's own preview menu visible - toggling the element preview switch clears the pin, which is why that path never broke). Covered by the new `element-preview-suspension.spec.ts`. TWO further causes of the broken previews were fixed in the same pass: (1) every re-apply started ANOTHER 1+16-step clip/fit loop on the SAME iframe (nothing stopped the loop of the previous load) and every step dispatched `resize`, which makes FORMCYCLE re-measure its cells - the loops accumulated, so the FIRST preview was correct while every later refresh thrashed the canvas and left it clipped with the platform preview chrome visible; a per-iframe GENERATION counter plus an `isConnected` check now ends a superseded loop and `fitPreviewHeight` dispatches `resize` only when the fitted height actually CHANGED (it is remembered in `data-codbi-fit-height`). (2) Dismissing the question (Später/ESC/backdrop) no longer re-actualises anything: `flushElementCssClassChange({ refreshPreview: false })` and `resumeElementPreviews(false)` keep the class saved (persist-differ nudge only) while skipping the `cssclasses` editor push and every preview refresh, so the canvas keeps showing what it showed before the question. (3) The preview HEIGHT PINS were the actual reason the layout drifted apart after two or three refreshes: `minHeight` is pinned on the element cell so FORMCYCLE cannot shrink the taller preview, but the pin outlived its preview - the designer re-renders cells IN PLACE, so a pin stayed on a cell whose iframe was replaced or gone and every further refresh pinned yet another cell (tall gaps, wrongly clipped boxes). The pins are now tracked in `pinnedPreviewWrappers` and `prunePreviewPins()` (run from every `refreshBadges`) releases a pin whose wrapper is detached or no longer contains its preview iframe; a reload also drops the stale fit RECORD and the remembered fitted height, and a pending debounced fit of a removed frame is discarded instead of dispatching `resize` for a preview that no longer exists. (4) The preview pipeline is now SELF-HEALING and storm-proof, which removes the last way a refresh could compound: `refreshBadges` reconciles every running preview's cell pin with its iframe's own height (`reconcilePreviewPin`), restarts a preview whose clip/fit loop died (the reload landed after its loop had been superseded, leaving it stuck at the initial 360px - `healRunningPreviews`, tracked via `previewClipLoops`), and a per-iframe burst guard (`MIN_PREVIEW_RELOAD_INTERVAL_MS`, `previewLastReload`) postpones - never drops - reload requests that arrive within 1.5 s, because a reload resets the iframe to 360px and restarts the fit loop, so unthrottled bursts never finished a single clip. Diagnostics: `window.CodbiPreviewDebug = true` prints one line per reload/postponed reload/fit/pin reconcile/pin release, so a remaining issue can be traced from the console. (5) The burst guard itself was ORDERED wrongly at first and therefore made things worse: it ran AFTER the reload had already reset the iframe to 360px, released the cell pin, dropped the fit record and bumped the clip generation - and then returned without pointing the iframe anywhere. A postponed request therefore left the cell clipped at 360px, unpinned, with its clip generation invalidated while `previewClipLoops` still claimed a live loop, so even the self-healing pass refused to restart it. Every refresh that produced more than ONE reload request (the confirm path produces three: class flush, standards property change, form-preview revision) broke the preview, and with the DevTools console open the extra latency made overlapping requests the normal case - hence `the moment the console is open it happens right away`. The guard now runs FIRST, before any state is touched: a postponed request changes nothing and simply retries after the window. Activation (button or confirmed dialog) goes through [`activateStandardConfig()`](src/main/web/packages/designer/src/js/ElementFunctionalityConfigEditor.ts:1220) — same three paths as before (`setStandardsValue` → `set-property` callback + `Active` flag → standards-tree checkbox) — and is remembered locally so the listing reflects it immediately. - **A new `codbi.canonical_output_rules` prompt guides the AI to emit Formcycle/CodBi JSON in the EXACT canonical format the server expects, so malformed output no longer triggers the token-heavy recovery passes.** The two observed failure classes were (1) conditional-visibility conditions stored with SWAPPED roles — `hiddenif` set to the controlling field's NAME or a mode number while `hiddenifcomp` held the mode (the canonical form is `hiddenif` = the controlling element's TECHNICAL id (e.g. `xi-cb-showpersondata`), `hiddenifcomp` = the EConditionType code 0-9, `hiddenifclear` = `"false"`, `hiddenifvalue` = the comparison value) — and (2) CodBi functionalities (e.g. `CodBi_NoFutureDate`) appended to the element's `cssclasses` list instead of being expressed as `kind:"func"`/`kind:"param"` (with `"codbi":true`) attributes. The server normalizes such deviations automatically, but that corrective normalization is what triggers the extra full-form re-send that inflates `tokensIn` (each recovery pass re-sends the whole form JSON). The new rules are injected into BOTH the pass-1 decision prompt (`buildCodbiFormSystemPrompt`) and the pass-2 apply prompt (`loadCodbiApplyPrompt`) so the AI emits canonical output on the first pass. Registered in `prompts/index.json` and auto-seeded like every other prompt resource. Saves one or more full-form re-sends per run whenever malformed CodBi output previously occurred.
- **A targeted rerun no longer re-sends the ENTIRE form to the AI in pass-2.** When a rerun is targeting only a subset of the form (elements requested by pass-1), the pass-2 user content previously dumped the whole `slimPersistJson(formBase)` — every untouched leaf in full — which is the single largest `tokensIn` multiplier of the pipeline. A new `sliceFormForPass2` helper now sends ONLY the targeted items plus the full container/page items, collapsing the untouched leaf majority to structural `{className, properties:{name, id}}` stubs (e.g. a 100-field form that targets 3 widgets now sends those 3 in full + the page/container/item structure + ~97 tiny stubs instead of ~97 full leaf bodies). The payload carries an explicit instruction telling the AI that stubs are the untouched remainder the server keeps verbatim and that it must NOT echo them back, so it returns only the full modified/new items and any containers it re-shapes. Defense-in-depth: `splicePass2IntoPass1` gained an `isLeafStubItem` guard, so even if the AI echoes a stub contrary to the instruction, the stub can never SUBSTITUTE for (thereby deleting the configuration of) a real pass-1 item — the full item is kept and the stub's id/name is marked consumed so it is not appended as a duplicate new item. No information is lost: whatever the AI does not re-emit is preserved verbatim by the existing splice merge.
- **Untouched leaf elements can now be OMITTED from a pass-2 output (and even from the forced final pass) instead of re-emitted byte-for-byte — a top-level `_unchangedItems` hint further cuts `tokensOut`.** Both the pass-2 apply prompt and the forced final-pass prompt now tell the AI that a LEAF element (widget/field) whose body it is NOT changing and whose position has NOT changed may be dropped from its output entirely if it lists the element's exact `properties.name` in a top-level `"_unchangedItems": ["elementName", ...]` array — the server then keeps that element verbatim from the form base. Containers and pages are never eligible (they always define the tree, so they must be emitted in full with their complete `elements` array), an element that was moved/re-ordered must be re-emitted normally (never listed as unchanged), and an element being removed goes in `_removedItems` (never `_unchangedItems`; if a name appears in both, removal wins). Server-side, `splicePass2IntoPass1` simply keeps any pass-1 item that is not re-emitted (the existing `replacement ?: item` merge already preserves it) and strips `_unchangedItems` from the merged object before serialization, so the hint can never leak into the published form as a designer-hostile top-level field. No information is lost: whatever the AI omits and lists is preserved verbatim.

### Changed
- **The AI assistant prompts are dramatically leaner (less AI token usage per run) without losing any decision rules the AI needs to build forms/workflows correctly.** Three new lean prompt variants were added and wired into the run pipeline, so every pass in `AICodBiAssistant` now sends only the decision-relevant core instead of the full general reference:

  - **Element structure reference** (`codbi-form-structure-rules.md`) was compressed from ~58.4 KB to ~37.5 KB.
  - All three new keys are registered in `prompts/index.json` and wired with a **fallback-safe chain** (`codbi.general_rethink → codbi.general_decision → codbi.general`) so existing databases that have not yet reseeded keep working, and the new keys auto-serve from the classpath on hot-deploy.

### Changed
- **Custom JavaScript is now attached to a FORM ELEMENT, never to the form**: the form-level `_customScript` marker and the `codbi-prop-custom-script` form property were REMOVED — `FormRenderCallback` no longer injects a form-wide `<script>` into the rendered form, `CodbiFormProperties.customScript` and the marker handling in `AIFormAssistant`/`AICodBiAssistant` are gone. - **Multilingual workflow mails on whole-form translation (`FC_SWITCH` on `[%lang%]`)**: when the form
  AI translates a whole form into ADDITIONAL languages, it now also emits a structured, language-
  agnostic marker (`"_workflowMailLanguages": ["<baseCode>", "<addedCode>", ...]`, base language
  first — same model-declared-signal pattern as `_codbiApplicability`, never a server-side keyword
  guess). When the marker is present and a workflow version is available, `AICodBiAssistant` runs a
  dedicated multilingualize pass (`runWorkflowMailMultilingualization`, prompt
  `codbi.workflow_translate_instruction` / `codbi-workflow-translate-instruction.md`): the AI names the
  existing **consumer-facing** `FC_EMAIL`/`FC_DOI_INIT` nodes (recipient = a `[%…%]` consumer email
  field or a DOI invitation; internal/admin/error mails are skipped) and provides the subject/body
  translation per added language. The backend then wraps each chosen node **in place** into an
  `FC_SWITCH` with `switchValue="[%lang%]"` (Formcycle's native placeholder for the language the form
  was filled out in — verified in the official howto
  `help8.formcycle.eu/…/103000047241-internationalisierung-im-workflow` and against
  `FcSwitchExecutor`, which resolves the switch value through the condition operand mapper). The
  original mail stays byte-for-byte on the base-language `FC_SWITCH_CASE` and the
  `FC_SWITCH_DEFAULT`; every other language gets a clone with translated subject/body/senderName while
  `to`/`from`/attachments/DOI pages and all placeholders are preserved. The switch keeps the mail's
  position, so the lane's continuation after it is untouched — no new lane/trigger/endpoint is created,
  and no submit button or field is added. The marker is stripped from the form before it is saved.
  Prompt rules were added to both form prompts (`codbi.form_structure_rules`,
  `formcycle.general`) and registered in `index.json`; covered by the FS12 scenario in the whole-form
  test-prompts plan.
  The assistant dialog (`ai-assistant.ts`) now also sends `workflowVersionId` on **form-only** runs
  when a workflow exists (previously workflow/both only), so the translation run reaches the
  multilingualize pass; the existing "formJson + workflowMessage" response handling then publishes the
  translated form and reloads the designer to show the new switch.
  The multilingualize pass feeds the model only a **condensed candidate list of the FC_EMAIL /
  FC_DOI_INIT nodes** (id, name, type, params) plus an explicit output rule instead of the whole
  workflow tree (feeding the full tree made the model echo the workflow back instead of answering the
  small mails payload, so no switch was created), and **retries once with a strict schema instruction**
  when the reply contains no usable `targetNodeId`+`translations` entry — the form translation itself
  is never failed when this optional pass yields nothing. The candidate collector descends through
  both `children` and the task-level `rootNode` of the workflow-structure JSON (the node tree lives
  under `rootNode`; without that descent it found zero mail nodes and skipped the wrap — observed
  "no FC_EMAIL/FC_DOI_INIT node found - nothing to wrap").
  **Which mails are consumer-facing is the AI's own decision** — no server-side filter is applied (a
  deterministic filter can never cover every way a mail is destined to the consumer or an internal
  office). The model must therefore return an explicit `toConsumer` boolean for **EVERY** candidate
  node in a single pass (verdict + translations together): the runner validates that no candidate is
  missing a verdict and **retries once with a strict schema instruction** (listing the missed ids)
  when any candidate lacks a verdict or the reply is unusable; it then wraps ONLY the nodes the model
  itself marked `toConsumer: true` and leaves internal/back-office/error mails untouched. Live
  validation had shown the model wrapping almost every mail node (including "Benachrichtigung für die
  Sachbearbeitung" and "E-Mail an Kasse"); the workflow-translate prompt now gives intent-based
  guidance (who reads the mail and what it is for) instead of relying on recipient strings or keyword
  lists.
- **Whole-form translations never trigger the CodBi "blind" re-evaluation pass**: both form
  assistants (`AICodBiAssistant`, `AIFormAssistant`) now skip that second pass (which re-sends the
  whole large form and can exceed the model's output limit → "AI returned invalid JSON") whenever the
  form-AI response declares the structured `_workflowMailLanguages` translation marker — even when the
  model omitted `_codbiApplicability` entirely. A whole-form translation only ADDS per-language text
  fields and never a CodBi element, so the blind CodBi re-evaluation is pointless and harmful for it.
  The form-AI prompt reminder also now asks the model to emit `_workflowMailLanguages` (base language
  first) plus `_codbiApplicability.codbiVerdict = "none"` on every whole-form translation.
- **Later language additions EXTEND an already-multilingual mail `FC_SWITCH` instead of wrapping it
  again**: when the whole form is translated into languages that a previously created `[%lang%]` mail
  switch does not cover yet (e.g. "Übersetze das Formular ins Englische und Französische." on a form
  whose de/it `FC_SWITCH` was built by an earlier run), the mail pass no longer leaves English/French
  consumers on the German default mail. The candidate collector now feeds the AI two kinds of
  candidates — `"MAIL"` (a plain `FC_EMAIL`/`FC_DOI_INIT` to wrap) and `"SWITCH"` (an existing
  `[%lang%]` `FC_SWITCH` already carrying translated mail clones, reported with its
  `existingCaseLanguages`, `defaultBranchId` and the first clone's type/name/params) — and it does not
  descend into a handled `[%lang%]` mail switch's subtree, so clones are extended, never re-wrapped.
  The model is told to translate a SWITCH only into the form languages missing from its
  `existingCaseLanguages`. The apply loop dispatches per kind: a SWITCH candidate goes to the new
  `extendMailSwitchNode`, which appends one `FC_SWITCH_CASE` (+ `SEQUENCE` + translated mail clone
  named "<switch name> (<lang>)") per added language under the SAME switch; the `FC_SWITCH_DEFAULT`
  stays at index 0 (the FIRST child — Formcycle requires the default as the first branch or the
  switch is INVALID) via `ensureSwitchDefaultFirst`, which also heals switches that were generated
  with the default placed last. Verified against the de/it form: a follow-up
  de→en+fr run now yields `Extended existing FC_SWITCH … with new language case(s): en, fr` with the
  en/fr branches inserted before the default.
- **Multilingual Abschlussseiten (ending pages) by REUSE — never created**: the ending-page pass that
  was parked (server-side creation of TEMPLATE_CLIENT rows is impossible from the plugin: no JPA
  entity, encrypted `TEXTVALUE`, no creation API) is now active in a reuse-only form. When a whole-form
  translation adds languages, `AICodBiAssistant` additionally wraps every consumer `FC_SHOW_TEMPLATE`
  (Abschlussseite) node into an `[%lang%]` `FC_SWITCH` (same trigger/marker and same verdict-only
  single-pass + strict-retry pattern as the mail pass: the model returns a `toConsumer` verdict per
  condensed candidate, never the whole tree). Each non-base case points at the **already existing**
  localized page whose NAME is `<base> _CB_<LANG>` (e.g. `Formular versendet _CB_EN`; `de-CH` →
  `_CB_DE-CH`) — resolved deterministically by the backend from the client's `TEMPLATE_CLIENT` rows
  (NAME + UUID are plain text; the encrypted content is never read) via the new
  `listClientTemplates` / `findLocalizedTemplate`. When no localization exists the case falls back to
  the **original** page — a page is never created, invented or edited. An already-`[%lang%]`-wrapped
  ending-page switch is EXTENDED with the missing languages (new `extendEndPageSwitchNode`, mirror of
  `extendMailSwitchNode`), never double-wrapped. `handleRun` runs the ending-page pass right after the
  mail pass (both under the same `_workflowMailLanguages` gate + `workflowVersionId`) and emits one
  combined `workflowMessage`. The obsolete page-creation helpers
  (`ensureEndPageForLanguage`, `setTemplateText`, `setNewUuid`, `readTemplatePage`, …) are marked
  SUPERSEDED/inert.
- **Multi-language whole-form translations run ONE LANGUAGE PER AI PASS (sequential)**: when a request
  asks to translate the whole form into two or more NEW languages at once ("translate to English and
  French"), the backend no longer lets a single AI response carry every translation — that oversized
  output truncated mid-JSON on large forms (observed live at 15587 chars) and aborted the run before
  the workflow passes. The new `planWholeFormTranslation` (model-declared languages, reached via a
  cheap fallback-safe hint — the AI decides, never keyword parsing) detects the multi-language case;
  `runSequentialWholeFormTranslation` then reuses the proven single-language form pipeline
  (`runFormModification`) once per language on the ORIGINAL persist, each pass restricted to its one
  language, and merges the per-language i18n (labels/headers/legends/rtevalues plus nested
  per-option/per-button i18n) into a single final form via `overlayLanguageI18n`. `handleRun` engages
  this only when ≥2 new languages are planned (otherwise the normal single pass is unchanged), and it
  overrides the `_workflowMailLanguages` list to the full base-first set so the ONE combined mail +
  ending-page multilingualization runs afterwards for all languages.
- **`FC_SWITCH` children obey Formcycle's required layout — default branch at index 0**: a switch node
  is INVALID in Formcycle unless its `FC_SWITCH_DEFAULT` branch is the FIRST child
  (parent_order_idx 0); the language `FC_SWITCH_CASE`s follow it. All multilingualize builders now
  create the default branch first (mails + ending pages), the extenders no longer move the default to
  the end, and the new `ensureSwitchDefaultFirst` reorders any switch whose default is not the first
  child — so a re-run of the same translation request also heals switches that earlier runs generated
  with the default last (observed live: ending-page switch had case(0), case(1), case(2), default(3)
  and the extended mail switch had its default forced to index 5). The workflow-AI switch builder
  already followed this convention.
- **Repeat whole-form translations are form no-ops (no more invalid-JSON aborts)**: when the request is
  a whole-form translation but EVERY named language is already present on the already-multilingual form
  (e.g. re-running "Übersetze das Formular ins Englische und Französische." after en+fr were added), the
  backend no longer re-runs the generic full form-rebuild pass — that pass re-emitted the whole
  multilingual form, exceeded the output budget and returned truncated, single-quoted invalid JSON
  (observed live at 17366 chars), aborting the run before the workflow passes. The translation-plan AI
  now reports `translationRequest=true` even for such repeat requests (with `addLanguages=[]`), and
  `handleRun` then leaves the form unchanged and still runs the workflow multilingualize (mails +
  ending pages), which verifies coverage and heals `FC_SWITCH` ordering.
