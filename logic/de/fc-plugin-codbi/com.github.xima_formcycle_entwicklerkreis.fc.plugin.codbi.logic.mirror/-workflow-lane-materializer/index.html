WorkflowLaneMaterializer

object WorkflowLaneMaterializer

Phase-1-Komponente: Materialisiert die ACTION LANE eines gespiegelten Workflow-Pfads in der reflektierenden Formulars eigene aktive „WorkflowVersion“ durch Umschreiben der vorhandenen Lane-Knoten IN PLACE.

Warum in-place (übernommen von Phase 0 Go/No-Go)

Phase-0-Lauf 2 hat bewiesen, dass die „customParameters“ eines bereits vorhandenen Downstream-Knotens mutiert wurden wird vom Executor im selben Trigger berücksichtigt (der Datensatz wird auf den neu gesetzten übertragen). Zustand). Phase-0-Lauf 1 bewies das Gegenteil für das Einfügen eines NEUEN Knotens: Es wird NICHT erneut durchlaufen Gleicher Auslöser. Der Materializer erstellt oder löscht daher niemals Knoten – er durchläuft die Quelle Pfad und die reflektierende Spur im Gleichschritt (Geschwisterindex innerhalb des übergeordneten Elements) und schreibt jede neu passende Parameter des reflektierenden Knotens (und Name/Typ, falls sich die Quelle geändert hat) auf demselben Knoten Referenz**, bleibt dann über „WORKFLOW_NODE_API.update“ bestehen.

Komponentengrenze (Phase 1)

Dieses Objekt entscheidet NICHT, wann es erneut materialisiert (das ist das Einchecken der Revision in Phase 2). MirrorNodePlugin.execute) und lokalisiert NICHT die reflektierende Spur (Phase 2 passiert das Ziel „WorkflowNode“ verweist auf RewriteRequest.targetChildren). Verantwortlichkeiten der Phase 1:

  1. Lesen Sie den Knoten TREE des Quellpfads (mit „customParameters“ und Geschwisterreihenfolge) über WorkflowMirrorAccess.sourceLane.

  2. Ordnen Sie die „customParameters“ jedes Quellknotens aus Referenzen im Quellprojektbereich neu zu Referenzen mit Zielprojektbereich (Workflow-Status-UUIDs nach NAME; andere Referenzen mit Gültigkeitsbereich werden durchgelassen mit einer Warnung).

  3. Schreiben Sie den passenden Zielknoten an Ort und Stelle neu (setCustomParameters/setName/setType + WORKFLOW_NODE_API.update), ohne Neuordnung oder Neuzuordnung.

  4. Markieren Sie die widerspiegelnde „WorkflowVersion“ als „workflowInvalid“, damit das Workflow-Modell neu geladen wird.

Der gesamte FORMCYCLE-API-/Entitätszugriff verwendet genau wie Reflektion (fc-common ist der bereitgestellte Bereich). WorkflowMirrorAccess und die Phase-0-Probe in „MirrorNodePlugin“.
