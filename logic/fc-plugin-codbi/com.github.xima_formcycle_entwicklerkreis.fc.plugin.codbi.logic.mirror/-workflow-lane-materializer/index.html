WorkflowLaneMaterializer

object WorkflowLaneMaterializer

Phase-1 component: materializes a mirrored workflow path's ACTION LANE into the reflecting form's own active WorkflowVersion by rewriting the existing lane nodes IN PLACE.

Why in-place (carried from the Phase-0 Go/No-Go)

Phase-0 Run 2 proved that mutating an already-existing downstream node's customParameters is honored by the executor in the same trigger (the record transitioned to the newly-set state). Phase-0 Run 1 proved the opposite for inserting a NEW node: it is NOT re-walked same-trigger. The Materializer therefore never creates or deletes nodes — it walks the source path and the reflecting lane in lockstep (sibling index within parent) and rewrites each matching reflecting node's params (and name/type if the source changed) on the same node reference, then persists via WORKFLOW_NODE_API.update.

Component boundary (Phase 1)

This object does NOT decide when to re-materialize (that is Phase 2's revision check in MirrorNodePlugin.execute) and does NOT locate the reflecting lane (Phase 2 passes the target WorkflowNode refs in as RewriteRequest.targetChildren). Phase 1 responsibilities:

  1. Read the source path's node TREE (with customParameters and sibling order) via WorkflowMirrorAccess.sourceLane.

  2. Remap each source node's customParameters from source-project-scoped references to target-project-scoped ones (workflow-state UUIDs by NAME; other scoped references pass through with a warning).

  3. Rewrite the matching target node in place (setCustomParameters/setName/setType + WORKFLOW_NODE_API.update), without reordering or re-parenting.

  4. Mark the reflecting WorkflowVersion workflowInvalid so the workflow model reloads.

All FORMCYCLE API/entity access uses reflection (fc-common is provided-scope) exactly like WorkflowMirrorAccess and the Phase-0 probe in MirrorNodePlugin.
