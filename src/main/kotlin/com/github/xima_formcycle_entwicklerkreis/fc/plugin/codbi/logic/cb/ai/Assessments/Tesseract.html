Overview

TesseractAction is a feature-rich in-process OCR service with support for single and multi-file OCR, regex extraction/verification modes, field-level extraction, orientation detection (OSD), image preprocessing, and resource-threshold gating. It integrates tightly with Formcycle servlet entry points and uses JNI-based tess4j.

Strengths

Broad OCR capability surface: print, extract, verify, and extract-fields modes are all supported through one endpoint.
Operational safeguards exist via resource monitoring (CPU/RAM thresholds) to protect server stability under load.
Image quality pipeline is robust: DPI awareness, orientation detection, rotation transforms, binarization, and denoising.
Pool-based Tesseract handle strategy is appropriate for throughput and avoids repeated cold-start init cost.
Good practical logging throughout preprocessing, DPI handling, and OCR flow, which helps support and incident analysis.

Weaknesses & Risks

Class scope is very large and multi-responsibility. Transport concerns, OCR orchestration, image processing, metadata parsing, regex extraction, and lifecycle state are all in one class.
Recommendation: extract internal collaborators (for example OcrModeHandler, ImagePreprocessor, DpiUtil, OrientationService) to reduce regression risk and improve test isolation.
Potential resource-pressure hotspots. In-memory image transforms and temporary file generation can spike memory/IO under heavy concurrent uploads.
Recommendation: add explicit image dimension/size caps before expensive transforms and add bounded temp-file cleanup guarantees.
Regex execution is user-driven. Complex or pathological regex patterns can be expensive and may degrade response times.
Recommendation: add regex complexity safeguards (timeout strategy or pattern restrictions) for request-supplied expressions.
Shared static instance model limits flexibility. Companion instance state may complicate multi-instance scenarios and testing.
Recommendation: prefer instance-bound routing in callers where feasible, using static access only as compatibility bridge.

Priority Recommendations

  1. Split class responsibilities into dedicated internal services for OCR modes, preprocessing, and orientation handling.
  2. Add hard limits for image dimensions and bytes before expensive processing.
  3. Introduce safeguards for user-provided regex patterns (complexity controls/timeouts).
  4. Gradually reduce static singleton coupling for easier testability and future multi-instance use.
