Assessment: Standard.kt

Date: March 14, 2026 | Branch: Designer_Interface | Repository: XIMA-formcycle-Entwicklerkreis/CodBi-Dev
File: src/main/kotlin/com/github/xima_formcycle_entwicklerkreis/fc/plugin/codbi/logic/cb/ai/llama/Standard.kt

Overview

Standard.kt is the central orchestrator for the local LLAMA server mode (and optional external API mode). It reads plugin properties, builds immutable configuration, initializes all commons services, manages model downloads, starts/stops server processes, handles thinking-server mode, and owns session/executor lifecycle concerns.

Strengths

Strong modular composition: most heavy responsibilities are delegated to focused collaborators (MessageBuilder, ChatCompletionService, WebSearchHandler, ThinkingServerManager, etc.).
Robust configuration parsing with sensible defaults and range checks in readPluginProperties (for example max tokens, compute/RAM limits, upload limits, search round-trip cap).
Good operational flexibility: supports local inference and external OpenAI-compatible endpoints, with consistent initialization path and logging for both modes.
Defensive runtime model: asynchronous startup, stale streaming-session cleanup, and clear separation of fast model and optional thinking model lifecycle.

Weaknesses & Risks

The class has very broad scope (configuration, lifecycle, threading, orchestration, download/startup flow), making it close to a god-class. This increases regression risk when touching unrelated features.
Split lifecycle bootstrapping into dedicated internal components: config bootstrap, service graph builder, and model runtime launcher.
Initialization path is complex and side-effect heavy (property parsing mutates base LLAMA state, multiple services are conditionally wired). This complexity is hard to fully cover with unit tests.
Add integration tests for key startup modes: local-only, external-only, thinking-model enabled, and failure-paths (download failure, server start failure, invalid properties).
Error propagation relies on mutable state flags (loadError, serverReady, isActive) updated from async tasks, which can make failure diagnostics timing-sensitive.
Introduce a dedicated startup state model (sealed states) to make readiness/failure transitions explicit and auditable.
Property key surface is large and partly stringly-typed, which is prone to typo-based misconfiguration.
Centralize property keys in a typed schema and generate validation/error reports at startup.

Priority Recommendations

  1. Extract startup/lifecycle orchestration into smaller internal components.
  2. Add mode-focused integration tests for success and failure startup paths.
  3. Introduce explicit startup state transitions instead of distributed readiness flags.
  4. Consolidate and validate plugin property schema with clearer startup diagnostics.
