# CodBi Form Structure Rules — DECISION CORE (pass-1)

This is the decision core for FORM STRUCTURE: how to classify the request into the right structural outcome and which rules are absolute. The full build syntax (exact parameter wiring, worked examples) is appended in pass-2 AFTER you request it. Use this core to DECIDE the structure; use pass-2 details to emit the exact properties.

MANDATORY STANDARD CLASSES ON PERSON FIELDS (the People standard is active in the shared form — ALWAYS apply): Vorname/Nachname/first/last-name field → cssclasses=["CodBi_People_Name"] (a first name AND a last name EACH get their own class); E-Mail/email → ["CodBi_People_Mail"]; German PLZ → ["CodBi_People_PLZ"]; Telefon/phone → ["CodBi_People_Phone"]; building/house-number → ["CodBi_People_BuildingNumber"]. A person field WITHOUT its CodBi_People_* class is a FAIL. MULTIPLE CODBI CLASSES ARE ADDITIVE — THERE IS NO "ONLY ONE CLASS" RULE: in an address group this is MANDATORY — the PLZ field gets ["CodBi_People_PLZ","CodBi_OpenPLZ_AC_SET_PLZ"], the street ["CodBi_OpenPLZ_AC_SET_Street"], the locality ["CodBi_OpenPLZ_AC_SET_Locality"], the building-number ["CodBi_OpenPLZ_AC_SET_BuildingNumber","CodBi_People_BuildingNumber"]. NEVER drop one class because another is present — a PLZ field without its OpenPLZ class (in an address group) is a FAIL.

WIDGET STRUCTURE DECISIONS:
- Only the widget classNames listed in the Formcycle widget reference are valid (all start with 'X', e.g. XButtonList, XTextField, XSelect, XPage). NEVER invent a className — there is NO standalone 'BUTTON' widget class.
- Buttons (submit, back, next) are NOT standalone widgets: define each button as an entry inside an XButtonList item's 'buttons' array (name, title, value, action). A workflow submit trigger (FC_FORM_SUBMIT_BUTTON) references that button by its 'name'.
- APPROVAL / REJECTION BUTTONS ("Genehmigen"/"Ablehnen", approve/reject): create BOTH buttons as entries of ONE XButtonList (the workflow binds to each by 'name', so "Genehmigen" and "Ablehnen" run DIFFERENT workflow lanes). NEVER ask for query parameters / a "?approval=approve" URL scheme / a callback URL / a link mechanism — the decision is the button click.
- STATE-DEPENDENT AVAILABILITY (DECISION — the crucial distinction): "verfügbar / sichtbar / erscheint / angezeigt (nur) im Status X" → the element is AVAILABLE (RENDERED AT ALL) only in those states → `statusdependent` + `viewstatus`. "AKTIV / aktiviert / nutzbar / bedienbar / bearbeitbar / freigegeben / enabled / schreibgeschützt im Status X" → the element STAYS VISIBLE but is READ-ONLY there → `readonly_statusdependent` + `readonly_viewstatus`. NEVER use statusdependent+viewstatus for an "aktiv/nutzbar/enabled" request — that would HIDE the element instead of only disabling it. For "only ACTIVE/USABLE in state X" emit readonly_statusdependent + readonly_viewstatus with the `[!]` marker on the state name. The workflow state NAME is a name, NEVER translated, and always the NAME the user wrote — never a UUID you ask for. The `*dependent` flags are the STRING "1" (NOT a JSON boolean).
- CONDITIONAL PROPERTIES (show / hide / lock / require) are DIRECT element properties, never attributes entries: `hiddenif`/`hiddenifcomp`/`hiddenifvalue`, `readonlyif`/`readonlyifcomp`/`readonlyifvalue`, `requiredif`/`requiredifcomp`/`requiredifvalue` — always emit all three (the value is the controlling field's EXACT id; `...ifcomp` is the EConditionType code). THERE IS NO `disabledif` / `availableif` PROPERTY: a "deaktiviert / disabled / ausgegraut wenn ..." maps to `readonlyif*` (visible but locked) or `hiddenif*` + `hiddenifclear` (hidden AND disabled). Availability by workflow STATUS or USER GROUP is a DIFFERENT mechanism (the state-dependent pair above), NOT hiddenif.
- WORDING → MECHANISM IS LANGUAGE-AGNOSTIC: match the MEANING, never a literal German keyword — the user may write German, English, Italian, Dutch, French, ...
- REUSE INSTEAD OF DUPLICATING (DUPLICATES ARE A FAIL): before adding an element, look for an existing element with the SAME PURPOSE (a submit button labelled "Senden", a rich-text editor, a field for the same value, a group container) and then MODIFY that existing element (keeping its EXACT `properties.name`) — never add a second one with a new name. THIS APPLIES TO TEXT ELEMENTS TOO: a designed/interactive text is EXACTLY ONE XSpan — never a SECOND XSpan carrying the same text. A rebuild/rerun pass must MODIFY the existing XSpan instead of adding a copy.
- Every created widget MUST have a unique 'id' (e.g. 'xi-...') and a className from the reference list.
- There is NO 'row' className — never use 'xm-form-row' (or any similar name) as a className. To place fields SIDE BY SIDE on one line, give them the SAME 'rowid' property (see ROW GROUPING below).
- DEFAULT PLACEMENT OF A NEW ELEMENT = THE FIRST PAGE: when the request does NOT say where a new element (text, field, container, table, image, ...) shall go, append its 'name' to the FIRST XPage's "elements" array and set its properties.parentid to that page's 'name'. NEVER put it into the XHeader/XFooter (reserved for the navbar/language switcher/document-header items). Only an explicit location changes this.
- XUPLOAD DECISIONS: "Automatischer Upload" IS ALWAYS CHECKED — EVERY XUpload you create gets the direct property "uploadMode":"ajax" UNLESS the user explicitly wants upload-on-submit. "VORSCHAU"/"PREVIEW" is the FORMCYCLE preview (the direct boolean "filepreview":"1"), NOT a cropper — do NOT tag the upload with Media.Image.Cropper / a CodBi_Fotocropper_* class for a plain preview. "MEHRERE DATEIEN"/multiple files = the CodBi Media.MultipleUpload functionality applied ON that one XUpload (plus the native "uploadMultiple":"1"); it is NEITHER the cropper NOR the preview, and it creates EXACTLY ONE XUpload. Allowed extensions & per-file size are DERIVED from the requested file type (image/ID → common image+pdf globs ~4 MB; document → .pdf/.doc/.docx ~1 MB), never a clarification question.

ROW GROUPING RULES (RELATED fields that belong on the SAME LINE — decide these groups in ANY language):
- A person's GIVEN/FIRST name + FAMILY/LAST name (+ MIDDLE name) — up to three name fields share one line.
- A STREET/ROAD name + HOUSE/BUILDING number.
- A POSTAL CODE + LOCALITY/CITY (add COUNTRY/state when asked).
- An E-MAIL ADDRESS + PHONE/TELEPHONE (contact details).
- Any other fields the request presents as ONE unit (FROM+TO date pair, BEGIN+END pair, value+unit, quantity+size).
THE GOLDEN RULE — GROUP RELATED FIELDS, NEVER MORE THAN FOUR PER LINE: a line carries AT LEAST TWO and AT MOST FOUR fields; when MORE than four belong together split them over several lines ("row-1", "row-2", ...). Group ONLY genuinely related fields — never merge unrelated fields into one line. A related group of odd size keeps its own members together and remaining related fields go on the NEXT line. Fields that stand alone (single comment/message, checkbox, submit button) get NO 'rowid' and span their own full-width line. HOW Formcycle renders a row: keep the fields of one group as DIRECT SIBLINGS inside the same parent (do NOT wrap them); give ALL fields of one group the SAME string 'rowid' value; use a DIFFERENT 'rowid' per line; omit 'rowid' for full-width fields. NEVER copy a 'rowid' from another field — a rowid shared with a field of ANOTHER container merges ALL those fields into one row. Size the fields sensibly to share the line.

GROUP RELATED FIELDS INTO CONTAINERS (person / address / contact data): group logically-related fields into ONE dedicated XContainer (or XFieldSet when a legend/title fits) per group — do NOT place them flat on the page:
- NAME / person-data fields → one container (also the LDAP/autofill person-data group when one is requested).
- ADDRESS fields → one address container (the OpenPLZ autocomplete set lives here). CRITICAL — AN ADDRESS IS NEVER A SINGLE FIELD: when the request names "Adresse"/"Anschrift"/"address", build the FOUR parts `tfStrasse` (label "Straße"), `tfHausnummer` (label "Hausnummer"), `tfPLZ` (label "Postleitzahl", datatype "plzDE") and `tfOrt` (label "Ort") in that container, each with its OpenPLZ class, with street+house number on one `rowid` and PLZ+city on the next. A lone free-text "Adresse" XTextField is a FAIL.
- CONTACT fields (e-mail, phone/telephone) → one contact container.
Inside each container the fields are DIRECT SIBLINGS and the ROW GROUPING RULES still apply. Do NOT wrap a single line in its own extra container. Add each group container to its page's/container's 'elements' array and every field inside to the group container's 'elements' array; a field not referenced by any container's 'elements' array is orphaned and does NOT render.

COMPLETE FORM RULES (build the ENTIRE requested form): A request can contain MANY fields. Create EVERY field the user asked for in ONE output — never create only the most recent/emphasized subset and never drop fields mentioned earlier. "Make this group repeatable" applies ONLY to that one group — all OTHER requested fields must still be created. Map each requested input to the matching widget (single-line text → XTextField, multi-line → XTextArea, yes/no → XCheckbox / XSelect). Add every created field to its page's/container's 'elements' array. When in doubt, CREATE the field — a missing requested field is a failed request.

HELPTEXT AND RICH/INTERACTIVE TEXT — DECISION RULES: (1) the Formcycle "Hilfe"/"Help" of ANY element is its DIRECT property "helptext" — a "Hinweis"/help/hint request (ANY language) goes into that element's "helptext" — NEVER via HTML.SETAttribute + data-cb-name="title" (that is an HTML title tooltip, not the Formcycle Help). (2) a static text requested in a NICE / DESIGNED / INTERACTIVE style is a LANGUAGE-AGNOSTIC CONCEPT — write it as FULL styled HTML with a REAL interactive AND animated effect in the XSpan's `rtevalue` (headings + one styled card/box per point + a `@keyframes`/`:hover`/`<details>` animation). The animation CSS is a `<style>` block INSIDE the SAME XSpan's `rtevalue` (the CodBi `HTML.CSS` functionality does NOT work for `@keyframes`, so it must NOT be used here). (3) COMPOSE the content when only a topic is named — never ask for it and never emit an empty/placeholder text; a requested ILLUSTRATION ("eine animierte SVG Illustration", "SVG") becomes an INLINE `<svg>` INSIDE the SAME `rtevalue`, PROFESSIONAL/designed and animated (SVG SMIL and/or a CSS animation whose `@keyframes` live in the same `<style>` block).

PANEL FOLDING DECISION (start folded/collapsed — "zugeklappt", "eingeklappt", "collapsed by default"): CodBi panels default to UNFOLDED. To make panels START FOLDED, set the form-level GLOBAL VARIABLE HTML_PANEL_FOLDED to true (top-level 'variables' array) — ALL panels then start folded — and set data-cb-folded="false" on EVERY panel that must stay OPEN at the start. NEVER set the XFieldSet "collapsed" property (not a real Formcycle property). For folding existing AREAS: CONVERT THEM IN PLACE — keep the SAME item (same name/id/elements/children) and only ADD the panel functionality chosen by element type: on an XContainer/XContainerInvisible (div, NO legend) use data-cb-func=html.panel plus its parameters and NEVER a UI.Panels CSS class (those are FIELDSET-only and inert on a div); on an XFieldSet add the CSS class CodBi_HTML_Panel_Standard. NEVER put BOTH a panel class AND data-cb-func=html.panel on the same element. A converted panel MUST still list and contain ALL of its original child fields — omitting children renders an empty form and is a FAIL. A presentation-only change (folding/panels) must NEVER remove an input field.

PRESERVE EXISTING ELEMENTS & FUNCTIONALITIES — ABSOLUTE RULE (never remove what the user did NOT ask to remove): You MUST output the COMPLETE form — EVERY existing element from the input form must appear in your output (same name, id, className, properties, attributes) and stay in its original container — even when the request does not mention it. Only elements the user EXPLICITLY asked to remove may be omitted. Omitting ANY existing element/container/functionality is interpreted as a REMOVAL — that is data loss and an absolute FAIL. NEVER drop an existing data-cb-func / data-cb-* functionality from a field you are not asked to change. When the request targets ONLY some elements/properties, modify ONLY those.

RELATIVE PLACEMENT OF A NEW ELEMENT ("unter dem Container", "über dem Container", "below/above X", "neben X"): a POSITION named relative to an EXISTING element is NEVER that element's parent. "unter dem Container X"/"below"/"unterhalb"/"darunter" means the new element sits BELOW it, i.e. on the SAME LEVEL: add the new element's 'name' directly AFTER the reference's name in the 'elements' array of the REFERENCE's PARENT (page/container) and set its properties.parentid to that PARENT's 'id'. NEVER set parentid to the referenced container's 'id' and NEVER append to the referenced container's OWN 'elements' array. "über/oberhalb/darüber/above/before the first element/ganz am Anfang" → insert directly BEFORE the reference (position 0 when first). "neben X/next to X" → a SIBLING directly BEFORE or AFTER X in the PARENT's 'elements' array. ONLY an explicit "in den Container"/"im Container"/"into the container"/"inside" makes it a CHILD. When ambiguous between BELOW and INSIDE, choose BELOW. NEVER ask the user to clarify a relative position.

MOVING ELEMENTS (e.g. "den Senden-Button nach unten ans Formularende verschieben, nicht in einen Container"): Moving ONLY re-parents THAT element — remove JUST its name from the OLD parent's 'elements' array, add it to the NEW parent's 'elements' array, set its properties.parentid to the new parent's name. NEVER remove, drop, or empty any OTHER container/fieldset/panel while moving something. Keep the moved element's own properties and attributes unchanged.

PARTIAL HTML EDITS — WHEN A REQUEST TARGETS ONLY ONE PART OF AN ELEMENT'S HTML, CHANGE ONLY THAT PART: a single element's `rtevalue` may hold SEVERAL independent pieces (a designed text + a JS calculator + a weather forecast). A follow-up targeting ONE widget matches it by the heading/text it renders, re-emits the SAME element (same name/id), and keeps EVERY OTHER PART of its `rtevalue` BYTE-FOR-BYTE UNCHANGED (same text, same `<script>`/`<style>` blocks, same class names/order). NEVER blank/shorten/reorder/drop the other content, NEVER answer with just the improved widget, NEVER create a second element for a part that already exists.

WHOLE-FORM TRANSLATION — DECISION SUMMARY: a request like "übersetze das gesamte Formular ins Englische" is a TRANSLATE-THE-FORM request. It is fulfilled by ADDING per-language translation fields ("properties.i18n": { "<languageCode>": { "<property>": "<translation>" } }) — NOT by overwriting the base/default-language texts. Every element's 'name'/'id'/'className'/'cssclasses'/'rowid' and the ENTIRE CodBi wiring (data-cb-* attribute NAMES and TECHNICAL values: EP placeholders, [%fieldName%] placeholders, condition values, DataQuery names) stay byte-for-byte — never translated. When "translate" appears WITHOUT a target language, ASK which language. The output JSON must be COMPACT and MUST end with "_codbiApplicability": { "codbiVerdict": "none", "considered": [], "applied": [] } (a translation changes no CodBi element; this skips the server's second CodBi pass). When the translation adds a DIFFERENT language than the form's base, ALSO emit the "_workflowMailLanguages": ["<baseLang>", "<addedLang>", ...] server marker so consumer mails switch language. Translate EVERY consumer-visible text (label, legend, placeholder, helptext, page header/subheader, navbar options, select options, button titles, XSpan rtevalue content, dynamicAddText/dynamicDeleteText) — an untranslated visible text is a FAIL.
