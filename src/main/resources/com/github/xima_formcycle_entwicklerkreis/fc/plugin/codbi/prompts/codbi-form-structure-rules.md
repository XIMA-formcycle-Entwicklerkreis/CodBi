ROW GROUPING RULES (RELATED fields that belong on the SAME line) — group by MEANING, in ANY language:
- Given/first + family/last name (+ middle) — up to three share one line.
- Street/road + house/building number.
- Postal code + locality/city (+ country when asked — PLZ+Ort+Land = one line).
- E-mail + phone/telephone (contact).
- Any other fields the request presents as ONE unit (FROM+TO date, BEGIN+END, value+UNIT, quantity+SIZE).
THE GOLDEN RULE — GROUP RELATED FIELDS, NEVER MORE THAN FOUR PER LINE:
- HARD CAP OF FOUR: a line carries AT LEAST TWO and AT MOST FOUR fields. NEVER five+ on one line — split over SEVERAL lines ("row-1" first up-to-four, "row-2" next).
- Group ONLY genuinely related fields — NEVER merge unrelated fields to save space.
- An odd-sized group keeps its own members together, remaining related fields go on the NEXT line — NEVER fill a free slot with an unrelated field.
- Standalone fields (comment/message, checkbox, submit button) get NO 'rowid', spanning their own full-width line.
HOW Formcycle renders a row (there is NO 'row' widget/className — 'xm-form-row' is only the CSS class the renderer adds, never one you write):
- Keep a group as DIRECT SIBLINGS in the same parent (page/container 'elements') — do NOT wrap them in an extra container/fieldset, no wrapper per line.
- Give ALL fields of one group the SAME string 'rowid' in their 'properties' (e.g. "rowid":"row-1").
- Use a DIFFERENT 'rowid' per line ("row-1","row-2",…); omit 'rowid' (or empty) for full-width/standalone.
- NEVER COPY A 'rowid' FROM ANOTHER FIELD: a 'rowid' is only valid within the SAME container's related group — every OTHER field MUST have NO/empty 'rowid'. When you only add a CSS class or data-cb-* attribute (e.g. CodBi_HTML_Panel_AutoHeaderTitle_Supplement), do NOT add/copy/change its 'rowid' — a shared rowid across containers merges ALL those fields into ONE row.
- Size fields sensibly to share the line (two ≈ half each, three ≈ third each, four ≈ quarter each).

GROUP RELATED FIELDS INTO CONTAINERS (person / address / contact):
Group logically-related fields into ONE dedicated XContainer (or XFieldSet when a legend/title fits) per group — NOT flat on the page:

RELATIVE PLACEMENT OF A NEW ELEMENT ("unter dem Container", "über dem Container", "below/above X", "neben X"):
- A POSITION relative to an EXISTING element is NEVER that element's parent. "unter dem Container X"/"below the container"/"darunter"/"anschließend an" = the new element sits BELOW it, SAME LEVEL: add its 'name' directly AFTER the reference's name in the 'elements' array of the REFERENCE's PARENT (page/container) and set properties.parentid to that PARENT's 'id'. NEVER set parentid to the referenced container's 'id' and NEVER append the name to the referenced container's OWN 'elements'.
- "über dem Container X"/"oberhalb"/"darüber"/"above X"/"before the first element"/"ganz am Anfang" → insert the new 'name' directly BEFORE the reference's name in the PARENT's 'elements' (position 0 when the reference is the first child).
- "neben X"/"next to X"/"rechts/links von X" → a SIBLING directly BEFORE or AFTER X in the PARENT's 'elements'.
- ONLY when the user says the element shall be INSIDE ("in den Container","im Container","innerhalb","into the container","inside") do you make it a CHILD: set parentid to that container's 'id' and append its 'name' to that container's own 'elements'.
- "unter dem Container" is NOT "in den Container": a position phrase says WHERE in the form the element sits, not WHICH element contains it. When ambiguous between BELOW and INSIDE, choose BELOW (a sibling of the referenced container).
- The reference element comes from the request/context (e.g. "dem Container" = the container being discussed, usually the one from the previous request). Use its PARENT — do NOT invent a new wrapper container, do NOT ask to clarify a relative position.
- Example — "Füge eine Auswahl unter dem Container hinzu, der alle Ämter … anbietet.": the XSelect is a SIBLING of that container — parentid = the container's PARENT (the page), and its 'name' inserts directly AFTER the container's name in the parent's 'elements'. Putting it INSIDE (parentid = the container's id) is WRONG.

- NEVER remove/drop/empty ANY OTHER container/fieldset/panel while moving — an untouched container stays exactly as it is (children + place in its parent's 'elements'). Omitting an existing element/container is a REMOVAL, so every untouched element must remain in the output.
- Keep the moved element's own properties and attributes (e.g. the button's action, the checkbox's label) unchanged.

WHOLE-FORM TRANSLATION — ADD translations as per-language fields ('properties.i18n'):
"übersetze das gesamte Formular ins Englische"/"translate the whole form into Italian"/"traduire le formulaire en français" is a TRANSLATE-THE-FORM request: the form is MULTILINGUAL — Formcycle stores per-language translations in an element-local map, fulfilled by ADDING the requested language's translations as those per-language fields (NOT overwriting the base/default-language texts). Formcycle shows the translation in that language and falls back to the base property otherwise.
- STORAGE: every element's 'properties' may carry '"i18n": { "<languageCode>": { "<property>": "<translated text>", … } }'. The plain properties ('label','placeholder','legend',…) keep the BASE/default-language text byte-for-byte. 'languageCode' = Formcycle language code ('de','en','fr','it','es','nl',…). Example (translate into English):
  "properties": { "name": "tfVorname", "label": "Vorname", "placeholder": "Vorname eingeben", "i18n": { "en": { "label": "First name", "placeholder": "Enter first name" } } }
- PROCEDURE — determine the target language code from the request; when "translate" appears WITHOUT a target language, ASK (clarification) instead of guessing. Then, for EVERY element carrying user-visible text, KEEP every existing base-language property value unchanged and ADD (or merge into an existing '"i18n"') the translations for that ONE language under the SAME property names:
  - 'label' of every input widget (XTextField, XTextArea, XSelect, XCheckbox, XUpload, XSignature, XCaptcha, XRating, XAppointment, filterable text fields, …),
  - 'legend' of every XFieldSet and 'legend'/'header' of pages/sections,
  - 'placeholder' of input fields,
  - 'helptext', 'title'/'alt' where user-visible (e.g. XImage), and any other human-readable text property,
  - static XSpan/XText content ('rtevalue': headings, intro/explanatory paragraphs), an XBsLogin 'bs_btn_text', a repeatable container's 'dynamicAddText'/'dynamicDeleteText',
  - XSelect OPTIONS: keep the 'options' array (text + value) EXACTLY as-is and add the per-language display text into each option object's OWN '"i18n"': {"text":"Ja","value":"Ja","i18n":{"en":{"value":"Yes"}}} (the per-language translation lives under the key 'value'; never change the option's top-level 'text'/'value'),
  - XButtonList BUTTONS: keep each button's 'name'/'title'/'value'/'action' untouched and add per-language text into each button object's OWN '"i18n"': {"name":"btnWeiter","value":"Weiter","i18n":{"en":{"value":"Next","title":"Next"}}}.
NEVER translate/rename/touch (keep byte-for-byte identical):
- every element's 'name' and 'id' — a renamed 'name' breaks the whole structure ('parentid' and every 'elements' array keep referencing the SAME 'name's),
- every XSelect option's top-level 'value' and 'text', every XButtonList button's 'name' and 'action' — submit/next/previous triggers and conditions reference them,
- 'className', every 'cssclasses' entry (incl. all CodBi_* / AI_LLAMA_CHAT_* classes), 'rowid' and every structural/technical property,
- the entire CodBi wiring: the data-cb-func id, every data-cb-* attribute NAME, and every TECHNICAL attribute VALUE — EP placeholders ({ … }), [%fieldName%] / [%$…%] placeholders, field-referencing selectors/parameters (e.g. data-cb-field=".tfExtractedText", data-cb-replacements, hiddenif/hiddenifvalue), DataQuery names (data-cb-dataquery="HolaQuery"), the datacolumn parts in data-cb-columns, and any option 'value' a condition depends on.
So tfVorname stays tfVorname and option value "Ja" stays "Ja" — only the per-language fields ('properties.i18n[<lang>]' + per-option/per-button 'i18n') are added. The request changes ONLY translations: no add/remove/reorder, no layout/structure/conditions (hiddenif/readonlyif)/options/functionality/data-cb-* changes, and no edits to plain base-language display properties. Same elements, names, values, structure — translations appear only as '"i18n"' for the requested language. Do not invent an 'i18n' entry for a property with no base value, and never add an 'i18n' field for languages other than the requested one. When the target language IS the base language (the plain properties), no 'i18n' entry is needed.
- OUTPUT-SIZE / VALIDITY — a whole-form translation re-emits the COMPLETE form + translations, so output becomes large: emit the JSON COMPACTLY (no pretty-printing/indentation), NEVER emit an empty '"i18n": {}' (add 'i18n' only where at least one translation goes), translate every element's text in the SAME single output, and always finish the complete valid JSON (never stop mid-form).
- NO CODBI ELEMENT CHANGES — a translation never adds/changes/removes a CodBi element. So in your top-level output ALSO include `"_codbiApplicability": { "codbiVerdict": "none" }` — this marker tells the server no CodBi functionality applies, so it does NOT run a second CodBi evaluation pass (which would re-send the whole large form a second time and can exceed the model's output limit).
- COVER EVERY CONSUMER-VISIBLE TEXT — translate EVERYTHING the end user reads, not only the plain 'label'. Besides 'label'/'legend'/'placeholder', translate into the same 'properties.i18n[<lang>]' (and per-object 'i18n') maps every other visible text:
  - XPage: 'header' (page caption/title) and 'subheader' (subtitle under it) — both scalar properties resolved from 'properties.i18n' like a label: "properties": { "name": "Daten_Foerderung", "header": "Daten zur Förderung", "subheader": "…", "i18n": { "en": { "header": "Funding data", "subheader": "…" } } }
  - XNavigationBar: its nav 'options' are the visible step labels — translate each option's visible text like an XSelect option (per-option 'i18n', never the option 'value'): "options": [ { "text": "Angaben zur Förderung", "value": "Daten_Foerderung", "i18n": { "en": { "value": "Funding data" } } } ]
  - XSelect options and every XSelect-like list (radio groups, filterable selects, datalists, XNavigationBar): each entry keeps 'text'/'value' and gets '"i18n": { "<lang>": { "value": "<translated visible text>" } }'.
  - XButtonList buttons: each keeps 'name'/'value'/'action' and gets '"i18n": { "<lang>": { "value": "<translated label>", "title": "<translated title>" } }'.
  - XCheckbox/XUpload/XAppointment/XSignature 'label' and 'title', XTextArea/XTextField 'placeholder', XFieldSet 'legend', XSpan static 'rtevalue', XImage 'alt'/'title', repeatable containers' 'dynamicAddText'/'dynamicDeleteText', 'helptext'.
  RULE: if the end user can see it in the rendered form, it MUST receive a translation for the requested language — leaving a visible navbar step, page caption/subcaption, button label, select option, legend or static text untranslated is a FAIL.
- REQUIRED `_codbiApplicability` ON EVERY TRANSLATION OUTPUT — like every form output, a whole-form translation MUST contain the top-level `"_codbiApplicability"`. For a translation set `"_codbiApplicability": { "codbiVerdict": "none", "considered": [], "applied": [] }`. The server reads this verdict to SKIP its second CodBi evaluation pass — if missing, it re-runs the whole large form with the CodBi API, exceeding the output limit on big forms and returning invalid JSON. Include it at the very end, exactly like other `_codbiApplicability` outputs.
- MULTILINGUAL WORKFLOW MAILS — a whole-form translation makes the form MULTILINGUAL, and the mails the form's workflows send must follow the consumer's language. When the request translates the form INTO A DIFFERENT language than the base/default, your JSON output MUST ALSO end with the server marker `"_workflowMailLanguages": ["<baseLanguageCode>", "<addedLanguageCode>", …]` — a top-level JSON array listing the form's BASE language code first, then every language code THIS translation adds (exactly the 'languageCode' values you wrote into the '"i18n"' maps, e.g. `"_workflowMailLanguages": ["de", "en"]`). The marker tells the server to wrap each existing CONSUMER-facing FC_EMAIL / FC_DOI_INIT workflow node into an FC_SWITCH branching on the workflow placeholder `[%lang%]` (the language the form was filled out in) — the original mail stays on the base-language branch, a translated mail is generated for every other language. Emit the marker ONLY on a translation that ACTUALLY adds another language; a request that only edits the base language (or a non-translation change) NEVER emits it. Like `_codbiApplicability`, it is stripped before the form is saved and never becomes part of the form.

PARTIAL HTML EDITS — WHEN A REQUEST TARGETS ONLY ONE PART OF AN ELEMENT'S HTML CONTENT, CHANGE ONLY THAT PART: a single element's `rtevalue` may hold SEVERAL independent widgets (e.g. a designed text + a JS calculator + a weather forecast, each with its own markup and `<script>`). A follow-up such as "der Taschenrechner soll schöner aussehen / die Buttons nebeneinander … / eine Fade-in-Animation" targets ONLY that ONE widget: match it by the heading/text it renders, re-emit the SAME element (same properties.name and id) and keep EVERY OTHER PART of its rtevalue BYTE-FOR-BYTE UNCHANGED — same text, same other `<script>` blocks, same class names/ids, same order — while rewriting ONLY the targeted widget's markup, CSS and JS. NEVER blank/shorten/restyle/reorder/relocate/drop the other content of the same rtevalue, NEVER answer with just the improved widget or fresh plain text in place of the whole element, and NEVER create a second element for a part that already exists. An answer losing any previously generated part of the element is a FAIL.
