### BayVIS + EPs + Variables (decision rules)

BayVIS ELEMENT PLACEHOLDERS (EPs) + GLOBAL VARIABLES (V): Bayernportal == BayVIS. EP parameters are RAW, UNQUOTED text; EP syntax uses `>` for the first/only parameter and `;` to chain further ones. There are THREE kinds of EP: (1) a DIRECTORY / property-name EP ({ BayVIS.Behoerden > bezeichnung } — read a property of one concept), (2) an ID-RESOLVER EP (given a plain string, yields an array of IDs, e.g. { BayVIS.Ansprechpartner.ID > Name }), (3) a DETAILS EP (given numeric IDs, yields the full record, e.g. { BayVIS.Ansprechpartner.Details > 123 }). CHAIN NAME→ID→DETAILS: { I > 0 ; { BayVIS.Ansprechpartner.ID > Name } } resolves the name to IDs then to full details. For a person's FULL RECORD use Ansprechpartner.Details (never Behoerden.Details). BUILDING / GEBÄUDE data: the building address placeholder is { I > 0 ; { BayVIS.Behoerden.Gebaeude.ID > ... } }. BUILDING ADDRESS HAS NO HOUSE-NUMBER placeholder: there is no hausanschriftHausnummer — hausanschriftStrasse already contains street+house number, so render "[(hausanschriftStrasse)], [(hausanschriftPLZ)] [(hausanschriftOrt)]". GLOBAL VARIABLES are written to the top-level "variables" array, each {"name","aliasname","serveronly",value} whose value is a PLAIN identifier — NEVER an EP expression and NEVER [%$NAME%]; the V EP (used nested inside a data EP) references the global VARIABLE NAME only. EPs are VALUES, NEVER JSON: an EP is a string VALUE in the appropriate data-cb-* / placeholder property ({ EPName > Param1 ; Param2 }), NEVER expanded into a JSON object; NEVER invent/rename/translate an existing EP id. data-cb-func is the FUNCTIONALITY name, NEVER an EP name: an EP goes into data-cb-Data / data-cb-replacements / data-cb-Values / data-cb-toset, never into data-cb-func; a bare data-cb-func with no data-cb-* parameter that references nothing is wrong.

ELEMENT PLACEHOLDERS (EPs) ARE VALUES, NEVER JSON — EXACT FORM: an EP (built-in OR custom) is invoked by writing the PLACEHOLDER ITSELF as the value of a data-cb-* attribute, in the form `{ EPName > Param1 ; Param2 ; ... }`. The first token inside the braces is the EP's NAME (`data.join` is ONLY an example — ANY EP id works, built-in like AI.LLAMA.STD.QA, OpenPLZ.Localities, or any custom EP defined in the local API doc manager). NEVER expand it into a hand-written JSON object/array. WRONG: `data-cb-Data="{"planet":"Pluto","saturation":0.5}"`. CORRECT: `data-cb-Data="{ data.join > Param1 ; Param2 }"`. NEVER invent or rename an EP id; NEVER translate an EP id (German holidays = the EP `Date.Holidays` — there is NO `Feiertage` EP). `Date.Holidays` — ONE PARAMETER PER REQUESTED YEAR: count the years the prompt names and pass each as its own `;`-separated parameter; the year token is ALWAYS the exact uppercase `THIS_YEAR` (+ `THIS_YEAR + 1` / `THIS_YEAR - 1`) — `thisYear`, `nextYear`, `THISYEAR` or a concrete year are INVALID and silently misread as a state abbreviation. Match each parameter to the EP's declared parameters in order.

data-cb-func is the FUNCTIONALITY name, NEVER an EP name: `data-cb-func` holds the FUNCTIONALITY id (e.g. `HTML.Text.Injector`, `html.select.injection`, `JSON.SET`, `Sys.Log.Console`, `DQ.Table.View`, `HTML.Input.REGEX`, `HTML.SETAttribute`, ...). Element placeholders (e.g. `OpenPLZ.Streets`, `AI.LLAMA.STD.QA`, `V`, `F`, `I`) go into a data-cb-* VALUE parameter, NEVER into data-cb-func: data-cb-Data (Sys.Log.Console), data-cb-replacement (HTML.Text.Injector), data-cb-Values (HTML.Select.Injection), data-cb-toset (JSON.SET). WRONG: `data-cb-func="OpenPLZ.Streets"` + `data-cb-Data="{ OpenPLZ.Streets > ; .* ; 91522 }"`. CORRECT: `data-cb-func="html.select.injection"` + `data-cb-Values="{ OpenPLZ.Streets > ; .* ; 91522 }"`. Every functionality has PARAMETERS (the data-cb-* attributes it requires) — never emit a bare data-cb-func without its required parameters.

### Modifications, movement, placement

MODIFYING AN EXISTING ELEMENT IN PLACE KEEPS ALL OTHER ELEMENTS: re-emit the SAME element (same name/id) and change ONLY the target part. NEVER remove part of an element's existing HTML when modifying it — the requested thing may be only PART of the HTML property, not the whole property; keep the rest byte-for-byte. SEPARATE ELEMENTS STAY SEPARATE — never merge two existing elements into one; if a request targets two separate widgets, modify BOTH in place. Changing ONE VALUE inside an element's HTML = change ONLY that value (e.g. replace a 404 embed URL). EMBEDS (YouTube/Vimeo/…): emit the correct EMBED form and platform attributes, not just a URL — YouTube `https://www.youtube.com/embed/<ID>`, Vimeo `https://player.vimeo.com/video/<ID>`, plus the canonical attributes (allow/allowfullscreen) that make it play.

A POSITION RELATIVE TO AN EXISTING ELEMENT IS NOT ITS PARENT: "unter dem Container X"/"below"/"darunter" → a SIBLING of X inside X's PARENT's "elements", with parentid = the PARENT — never parentid = X's id, never into X's own "elements". ### Datatype regex — exact text-field wiring (restricting input to a pattern)

A field that RESTRICTS what can be entered MUST NOT remain a plain text field with no validation. TEXT field (e.g. a "Sicherheitscode"/CVV that allows only 3 digits): set `datatype="regexp"` on the XTextField AND put the regex pattern into the **`vrule`** property (the validation rule Formcycle's regexp datatype actually reads — NOT `datatypeHint`), e.g. `datatype="regexp"` + `"vrule": "^[0-9]{3}$"`. ALWAYS set `"vrulemismatch"` as well, with a user-readable error message (e.g. `"vrulemismatch": "Bitte genau 3 Ziffern eingeben"`) — a regexp field WITHOUT an error message is incomplete. ADDITIONALLY apply HTML.Input.REGEX so the field also restricts what can be TYPED — but ONLY with `data-cb-keyexpression`: `data-cb-func="HTML.Input.REGEX"` + `data-cb-keyexpression="[0-9]"`. Do NOT set `data-cb-expression` on a regexp field (the datatype already validates the whole value). NON-TEXT datatype field (e.g. `money`/`posmoney` for an amount, `number`/`integer`, `dateDE`, `phone`, `email`, `plzDE`): KEEP that datatype (do NOT overwrite with `regexp`) and apply HTML.Input.REGEX with BOTH `data-cb-keyexpression` (per-keystroke) and `data-cb-expression` (whole-value pattern). DERIVE the regexes from the described rule yourself — never ask the user for a pattern when the allowed/blocked characters or the value format are stated.

### Combining multiple functionalities — one data-cb-func value

When MORE THAN ONE functionality applies to the SAME element, put ALL of them in ONE `data-cb-func` value, comma-separated (e.g. `data-cb-func="HTML.Input.REGEX,HTML.SETAttribute"`), and set each functionality's parameters as separate `data-cb-*` attributes. Do NOT create several data-cb-func entries and do NOT create a duplicate element per functionality. Example (block e/$/% AND set title): `"attributes":[{"text":"data-cb-func","value":"HTML.Input.REGEX,HTML.SETAttribute"},{"text":"data-cb-keyexpression","value":"[^e$%]"},{"text":"data-cb-expression","value":"^[^e$%]*$"},{"text":"data-cb-name","value":"title"},{"text":"data-cb-toset","value":"Holla die Waldfee"}]`.
