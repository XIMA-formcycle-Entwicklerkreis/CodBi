### BayVIS + EPs + Variables (decision rules)

OBJECT-PRODUCING EPs AND MEMBER ACCESS (language-agnostic, ANY language): `Date.Today` delivers TODAY as a date OBJECT (`NOW` or NO parameter = today; `+1d` / `-2m` / `+1y` shift it) — an OBJECT, never a formatted string, so it must never be put into a `dd.MM.yyyy` / state / id parameter (`Date.Weekends`, `Date.Holidays`, `BayVIS.Behoerden.ID`). To READ A PROPERTY or CALL A PARAMETERLESS METHOD of such an object ("getMonth() von dem heutigen Tag", "the year of today", "die Eigenschaft … von …", "extract <property>") use `JSON.Path` in FIXED order — the OBJECT first, the PATH second: { JSON.Path > { Date.Today > NOW } ; getMonth() }. A plain path segment reads a property (`name`, `email`); a segment written `name()` — ROUND BRACKETS, NO SPACE — CALLS a parameterless method (`getMonth()`, `getFullYear()`, `toString()`). A bare member name is NEVER a value: `data-cb-Data = getMonth()` is INVALID and `{ Date.Today > }` with an EMPTY arithmetic slot is invalid too — `{ Date.Today }` or `{ Date.Today > NOW }` is today.

PARAMETER ORDER IS FIXED BY THE EP, NEVER BY THE WORD ORDER OF THE REQUEST (language-agnostic, ANY language): the `;` slots are filled in the order the EP DECLARES them, never in the order the sentence mentions the values. A Details EP takes the IDENTIFIER in slot 1 and the PROPERTY in slot 2 even when the property is named first ("die Mail-Adresse des Amts X") — `{ BayVIS.Behoerden.Details > email ; { BayVIS.Behoerden.ID > Amt für Digitales } }` is SWAPPED (property in the numeric-id slot) and returns nothing, correct is `{ BayVIS.Behoerden.Details > { I > 0 ; { BayVIS.Behoerden.ID > Amt für Digitales } } ; email }`. The same fixed-order rule covers EVERY multi-parameter EP; a swapped slot never "still works".

DIRECTORY EP vs DETAILS EP — ONE NAMED AUTHORITY'S FIELD (language-agnostic, ANY language): `BayVIS.Behoerden` / `BayVIS.Ansprechpartner` return ONE COLUMN of the WHOLE directory (every authority / every contact) — they can never select one named entry. A request for a SPECIFIC, NAMED authority's field ("die Mail-Adresse des Amt für Digitales", "die E-Mail der Behörde X", "the e-mail address of <authority>") is therefore `{ BayVIS.Behoerden.Details > { I > 0 ; { BayVIS.Behoerden.ID > <designation> } } ; <property> }` and NEVER `{ BayVIS.Behoerden > <property> }` (that returns that column for EVERY authority and ignores the named one). The directory EP is only for a LIST/selection of all authorities (e.g. Values of HTML.Select.Injection). Naming the SYSTEM ("aus dem Bayernportal", "aus der BayVIS", "from BayVIS") does NOT make the directory EP the right choice — the SUBJECT decides. NEVER COMPOSE AN EP ID FROM WORDS OF THE REQUEST (language-agnostic, ANY language): the EP catalogue is FIXED — states, regions, countries, years and topics are PARAMETERS of an existing EP, never part of its NAME and never a new property. Reported failure: "die diesjährigen Feiertage von Bayern und Hessen" → { Holiday.BavariaAndHesse > list } (that id does not exist and `list` is not a parameter); CORRECT: { Date.Holidays > by ; he ; THIS_YEAR } (Date.Holidays is the ONLY holiday EP, one parameter per state plus the THIS_YEAR token). When unsure whether an EP supports a value, REQUEST its details — never invent an id or a property. FORMCYCLE WIDGET TYPES ARE NOT EPs (language-agnostic): XHeader, XFooter, XPage, XSpan, XContainer, XContainerInvisible, XFieldSet, XTextField, XTextArea, XSelect, XUpload, XButton, XTable are the className values of the form JSON - they say WHICH element is built and are NEVER EP ids. To ACQUIRE a rendered page element (the header, a page, a span, a field, a container - "gib das Header-Element aus", "log the header element", "den Container X ausgeben", "das Element ganz oben") use { DOM.Query > <CSS selector> }, where the selector is the element id as #xi-header-1 or its name as .header1 (names are rendered as CSS classes); the EP returns the element itself, so never wrap it in another EP id. Reported failure: { XHeader > header1 } - CORRECT: { DOM.Query > #xi-header-1 }. EP ARGUMENT TYPES (language-agnostic): an EP parameter's declared VALUE TYPE is binding — several EPs take PLAIN STRINGS in a fixed format (Date.Weekends -> dd.MM.yyyy, Date.FromString -> a date string, Date.Holidays -> state/THIS_YEAR tokens, BayVIS.Behoerden.ID -> a designation), so a DATE OBJECT (Date.Today / Date.FromString / Date.Arithmetic) must NEVER be nested into such a string slot: { Date.Weekends > { Date.Today > } ; { Date.FromString > 01.12.2026 ; dd.MM.yyyy } } is WRONG, { Date.Weekends > 01.12.2026 } is CORRECT for a range that starts TODAY (ONE dd.MM.yyyy string = the range END, e.g. today … 01.12.2026); a BOUNDED range uses TWO strings, param 1 = START, param 2 = END: { Date.Weekends > 01.12.2026 ; 31.12.2026 } = December 2026 only (e.g. 'Wochenenden im Dezember 2026' / 'weekends in December 2026'). { Date.Today > } with an EMPTY arithmetic parameter is invalid too — { Date.Today } is enough.

BUILDING / GEBÄUDE ADDRESS — EXACT CHAIN (overrides any shorter shorthand below): an ADDRESS comes ONLY from `BayVIS.Behoerden.Details.Gebaeude`, which takes TWO id slots — slot 1 = AUTHORITY id, slot 2 = BUILDING id (optional slot 3 = property) — BOTH resolved from the SAME designation and EACH with its OWN `{ I > 0 ; ... }` wrapper: { BayVIS.Behoerden.Details.Gebaeude > { I > 0 ; { BayVIS.Behoerden.ID > Amt 44 } } ; { I > 0 ; { BayVIS.Behoerden.Gebaeude.ID > { I > 0 ; { BayVIS.Behoerden.ID > Amt 44 } } } } ; hausanschriftStrasse }. `BayVIS.Behoerden.Gebaeude.ID` alone (it turns an authority id into building ids) is NOT an address and must NEVER be the whole placeholder. A ONE-slot `Details.Gebaeude` call, or a building id in the authority slot, is INVALID. A DESIGNATION THAT CONTAINS DIGITS IS STILL A NAME ("Amt 44", "Behörde 12", "office 7", ANY language): never cut its digits out and use them as an id — the designation goes, complete, into `BayVIS.Behoerden.ID`.

BayVIS ELEMENT PLACEHOLDERS (EPs) + GLOBAL VARIABLES (V): Bayernportal == BayVIS. EP parameters are RAW, UNQUOTED text; EP syntax uses `>` for the first/only parameter and `;` to chain further ones. There are THREE kinds of EP: (1) a DIRECTORY / property-name EP ({ BayVIS.Behoerden > bezeichnung } — read a property of one concept), (2) an ID-RESOLVER EP (given a plain string, yields an array of IDs, e.g. { BayVIS.Ansprechpartner.ID > Name }), (3) a DETAILS EP (given numeric IDs, yields the full record, e.g. { BayVIS.Ansprechpartner.Details > 123 }). CHAIN NAME→ID→DETAILS: { I > 0 ; { BayVIS.Ansprechpartner.ID > Name } } resolves the name to IDs then to full details. For a person's FULL RECORD use Ansprechpartner.Details (never Behoerden.Details). BUILDING / GEBÄUDE data: an address placeholder is NOT BayVIS.Behoerden.Gebaeude.ID but BayVIS.Behoerden.Details.Gebaeude with its two id slots (authority id ; building id) — see BUILDING / GEBÄUDE ADDRESS above. BUILDING ADDRESS HAS NO HOUSE-NUMBER placeholder: there is no hausanschriftHausnummer — hausanschriftStrasse already contains street+house number, so render "[(hausanschriftStrasse)], [(hausanschriftPLZ)] [(hausanschriftOrt)]". GLOBAL VARIABLES are written to the top-level "variables" array, each {"name","aliasname","serveronly",value} whose value is a PLAIN identifier — NEVER an EP expression and NEVER [%$NAME%]; the V EP (used nested inside a data EP) references the global VARIABLE NAME only. EPs are VALUES, NEVER JSON: an EP is a string VALUE in the appropriate data-cb-* / placeholder property ({ EPName > Param1 ; Param2 }), NEVER expanded into a JSON object; NEVER invent/rename/translate an existing EP id. data-cb-func is the FUNCTIONALITY name, NEVER an EP name: an EP goes into data-cb-Data / data-cb-replacements / data-cb-Values / data-cb-toset, never into data-cb-func; a bare data-cb-func with no data-cb-* parameter that references nothing is wrong.

ELEMENT PLACEHOLDERS (EPs) ARE VALUES, NEVER JSON — EXACT FORM: an EP (built-in OR custom) is invoked by writing the PLACEHOLDER ITSELF as the value of a data-cb-* attribute, in the form `{ EPName > Param1 ; Param2 ; ... }`. The first token inside the braces is the EP's NAME (`data.join` is ONLY an example — ANY EP id works, built-in like AI.LLAMA.STD.QA, OpenPLZ.Localities, or any custom EP defined in the local API doc manager). NEVER expand it into a hand-written JSON object/array. WRONG: `data-cb-Data="{"planet":"Pluto","saturation":0.5}"`. CORRECT: `data-cb-Data="{ data.join > Param1 ; Param2 }"`. NEVER invent or rename an EP id; NEVER translate an EP id (German holidays = the EP `Date.Holidays` — there is NO `Feiertage` EP). `Date.Holidays` — ONE PARAMETER PER REQUESTED YEAR: count the years the prompt names and pass each as its own `;`-separated parameter; the year token is ALWAYS the exact uppercase `THIS_YEAR` (+ `THIS_YEAR + 1` / `THIS_YEAR - 1`) — `thisYear`, `nextYear`, `THISYEAR` or a concrete year are INVALID and silently misread as a state abbreviation. Match each parameter to the EP's declared parameters in order.

data-cb-func is the FUNCTIONALITY name, NEVER an EP name: `data-cb-func` holds the FUNCTIONALITY id (e.g. `HTML.Text.Injector`, `html.select.injection`, `JSON.SET`, `Sys.Log.Console`, `DQ.Table.View`, `HTML.Input.REGEX`, `HTML.SETAttribute`, ...). Element placeholders (e.g. `OpenPLZ.Streets`, `AI.LLAMA.STD.QA`, `V`, `F`, `I`) go into a data-cb-* VALUE parameter, NEVER into data-cb-func: data-cb-Data (Sys.Log.Console), data-cb-replacement (HTML.Text.Injector), data-cb-Values (HTML.Select.Injection), data-cb-toset (JSON.SET). WRONG: `data-cb-func="OpenPLZ.Streets"` + `data-cb-Data="{ OpenPLZ.Streets > ; .* ; 91522 }"`. CORRECT: `data-cb-func="html.select.injection"` + `data-cb-Values="{ OpenPLZ.Streets > ; .* ; 91522 }"`. ### Modifications, movement, placement

PRESERVE EXISTING ATTRIBUTES / FUNCTIONALITIES — ABSOLUTE RULE: you MUST output the COMPLETE form — every existing element stays (same name, id, className, properties, attributes) in its original container, even when not mentioned. Only elements explicitly asked to be removed may be omitted. NEVER drop an existing data-cb-func / data-cb-* from a field you are not asked to change.

REMOVING A FUNCTIONALITY FROM AN EXISTING ELEMENT: when removing a CodBi functionality, re-emit the element's ENTIRE "attributes" array WITHOUT the removed functionality's attribute entries (never omit the whole attributes key — the server restores it). If the removed functionality was a panel, also remove the panel CSS class. When the removal means the remaining element must be wrapped outward, create exactly ONE wrapper container (a plain, NON-repeatable container); do not duplicate content.

MOVING ELEMENTS PRESERVES EVERYTHING ELSE: moving re-parents ONLY that element — remove it from the old parent's "elements", add it to the new parent's "elements", set parentid to the new parent; keep the moved element's properties/attributes unchanged; never drop/empty any other container while moving.

MODIFYING AN EXISTING ELEMENT IN PLACE KEEPS ALL OTHER ELEMENTS: re-emit the SAME element (same name/id) and change ONLY the target part. NEVER remove part of an element's existing HTML when modifying it — the requested thing may be only PART of the HTML property, not the whole property; keep the rest byte-for-byte. SEPARATE ELEMENTS STAY SEPARATE — never merge two existing elements into one; if a request targets two separate widgets, modify BOTH in place. Changing ONE VALUE inside an element's HTML = change ONLY that value (e.g. replace a 404 embed URL). EMBEDS (YouTube/Vimeo/…): emit the correct EMBED form and platform attributes, not just a URL — YouTube `https://www.youtube.com/embed/<ID>`, Vimeo `https://player.vimeo.com/video/<ID>`, plus the canonical attributes (allow/allowfullscreen) that make it play.

A POSITION RELATIVE TO AN EXISTING ELEMENT IS NOT ITS PARENT: "unter dem Container X"/"below"/"darunter" → a SIBLING of X inside X's PARENT's "elements", with parentid = the PARENT — never parentid = X's id, never into X's own "elements". "neben X" → sibling directly before/after X in the parent. Only "in den Container X"/"im Container"/"inside" makes it a child. When ambiguous, choose BELOW.

DEFAULT PLACEMENT OF A NEW ELEMENT IS THE FIRST PAGE: when the location is not specified, append the new element to the FIRST page's "elements" and set parentid to that page — NEVER the header/footer (which are reserved for the navbar/language-switcher/document-header items). Only an explicit location changes this.

### Datatype regex — exact text-field wiring (restricting input to a pattern)

A field that RESTRICTS what can be entered MUST NOT remain a plain text field with no validation. TEXT field (e.g. a "Sicherheitscode"/CVV that allows only 3 digits): set `datatype="regexp"` on the XTextField AND put the regex pattern into the **`vrule`** property (the validation rule Formcycle's regexp datatype actually reads — NOT `datatypeHint`), e.g. `datatype="regexp"` + `"vrule": "^[0-9]{3}$"`. ALWAYS set `"vrulemismatch"` as well, with a user-readable error message (e.g. `"vrulemismatch": "Bitte genau 3 Ziffern eingeben"`) — a regexp field WITHOUT an error message is incomplete. ADDITIONALLY apply HTML.Input.REGEX so the field also restricts what can be TYPED — but ONLY with `data-cb-keyexpression`: `data-cb-func="HTML.Input.REGEX"` + `data-cb-keyexpression="[0-9]"`. Do NOT set `data-cb-expression` on a regexp field (the datatype already validates the whole value). NON-TEXT datatype field (e.g. `money`/`posmoney` for an amount, `number`/`integer`, `dateDE`, `phone`, `email`, `plzDE`): KEEP that datatype (do NOT overwrite with `regexp`) and apply HTML.Input.REGEX with BOTH `data-cb-keyexpression` (per-keystroke) and `data-cb-expression` (whole-value pattern). When MORE THAN ONE functionality applies to the SAME element, put ALL of them in ONE `data-cb-func` value, comma-separated (e.g. `data-cb-func="HTML.Input.REGEX,HTML.SETAttribute"`), and set each functionality's parameters as separate `data-cb-*` attributes. URL-PARAMETER TO GLOBAL VARIABLE = SV (LANGUAGE-AGNOSTIC - decide by MEANING, ANY language): "URL-Parameter X als globale Variable", "verlinke den URL-Parameter X", "Query-Parameter in Formularvariable", "link/bind/map URL parameter X as a global variable", "read the query parameter into a global variable", "pass a URL parameter to the workflow" -> copy the URL QUERY parameter into a CodBi global variable at form load with data-cb-func="SV" on an XContainer/XContainerInvisible/XFieldSet (create ONE invisible container coUrlParams when none exists), data-cb-Destinations="<GLOBAL_VARIABLE>" and data-cb-Sources="<URL_PARAMETER>" (CSV lists of EQUAL length, paired by index; names are case-sensitive). DECLARE every destination in the top-level "variables" array as {"name":"<NAME>","aliasname":"<NAME>","serveronly":false,"value":""} - an undeclared variable never reaches the workflow. NOT the V EP (it only reads a variable), NOT a hidden field/JSON.SET/literal value. WORKED EXAMPLE - "Verlinke den URL-Parameter Hoho als globale Variable.": variables += {"name":"Hoho","aliasname":"Hoho","serveronly":false,"value":""}; XContainerInvisible coUrlParams with attributes data-cb-func=SV, data-cb-Destinations=Hoho, data-cb-Sources=Hoho, on the first page. A missing URL parameter yields an empty string.

SV DOCUMENTATION TEXT (ALWAYS): when SV is used, add ONE plain XSpan child ("ishidden":"1", no styling) inside the SV container whose rtevalue states the mapping in the form's language: single "Dieses Element uebernimmt den URL-Parameter X in die globale Variable Y." / "This element copies URL parameter X into global variable Y."; multiple pairs ONE combined, natural sentence "Dieses Element uebernimmt die URL-Parameter A und B in die globalen Variablen X und Y." / "This element copies the URL parameters A and B into the global variables X and Y." (comma list + "und"/"and" before the last for 3+; NOT one separate sentence per pair). The XSpan is author-facing documentation inside the invisible container, is never shown to the user, and must not be omitted. Include it in the container's "elements" and set its parentid to the container's name.

SV NOTE HIDDEN PROPERTY (MANDATORY): the documentation XSpan of an SV element MUST have the Formcycle Hidden property CHECKED - "ishidden":"1" in its properties (the designer checkbox "Ausblenden"/"Hidden"). Do NOT rely on the surrounding invisible container and do NOT use "invisible" (not a Formcycle property) or a CSS class for this. A generated SV documentation XSpan without "ishidden":"1" is WRONG.

HTML.CSS CARRIER ELEMENT (MANDATORY): when a NEW element is generated only to carry CSS rules, use an XSpan with "ishidden":"1" in its properties (the Formcycle Hidden/Ausblenden checkbox CHECKED), data-cb-func="HTML.CSS" + data-cb-css = the ACTUAL rules, and a descriptive rtevalue naming the CSS purpose + target in the designer's language (e.g. "Wendet CSS an: Ueberschriften rot (h1 { color: red; })."). NEVER put only a <style> block into rtevalue, NEVER leave it empty or generic ("HTML.CSS"), and NEVER use "invisible", a CSS class or a parent element for the hiding. This is the same author-facing documentation pattern as the SV note.
