# Formcycle General

Cross-cutting Formcycle rules that apply across widgets and workflow nodes.

CRITICAL — EP PARAMETERS & V: EP parameters are RAW, UNQUOTED text (write { BayVIS.Ansprechpartner.Details > Salvatore Callari }, NEVER { ... > "Salvatore Callari" }). A literal person/authority NAME is NOT a variable — variable names NEVER contain spaces. The V EP takes ONLY a GLOBAL VARIABLE NAME (e.g. SALVATORE_CALLARI_CONTACT, BayVIS_Behoerde); NEVER a name with a space / a quoted person name. { BayVIS.Ansprechpartner.Details > { V > Salvatore Callari } } is WRONG — use { BayVIS.Ansprechpartner.Details > Salvatore Callari } directly. Use V only for an explicitly requested global variable that exists in the top-level "variables" array.

## Form Structure Rules

- The 'items' array is FLAT at the top level — all form elements live here, including containers, fieldsets, and their children. Each item's unique identifier is stored in 'properties.name' (NOT as a top-level 'name' field — items have no top-level 'name'). Containers and fieldsets reference their children via 'properties.elements', a sub-array of child name strings (NOT the items themselves).
- When ADDING new items: append them to the top-level 'items' array AND add their name to the 'properties.elements' array of the target container/fieldset. EXCEPTION — a newly created INTRO/DESCRIPTION element that the user asks to place "at the beginning" / "before the first element" / "ganz am Anfang" / "vor dem ersten Element" MUST be INSERTED at POSITION 0 of the target container's/page's 'elements' array (so it renders first), not appended at the end; every OTHER existing element keeps its relative order — only the new intro element is inserted at the front.
- MANDATORY for containers/fieldsets: When creating a section/group that CONTAINS specific input fields, you MUST create ALL child input items in the same response. Do NOT output a container with an empty 'elements':[] when asked for content inside it. Each child item must appear both in the top-level 'items' array AND by name in the container's 'elements'.
- Assign unique, descriptive values to new items' 'properties.name'. Use type-appropriate prefixes: 'tf' for XTextField/XTextArea, 'fd' for XUpload, 'sel' for XSelect, 'cb' for XCheckbox, 'btn' for XButtonList buttons, 'sig' for XSignature, 'div' for XContainerInvisible.
- MANDATORY — EVERY generated element MUST have a unique 'id' property. The 'id' is the HTML/DOM element identifier and must be unique within the form. Convention: use the prefix 'xi-' followed by the element name (e.g., name="tfVorname" → id="xi-tf-Vorname"). Do NOT reuse 'id' values.
- MANDATORY — Every generated element's 'label' (and every XFieldSet's 'legend') MUST be a MEANINGFUL, descriptive, human-readable text that names the field's purpose, written in the SAME language as the user's request (e.g. "Straße", "Postleitzahl", "Ort", "Land" for an address form). NEVER use generic placeholders such as "Label", "Example", "Text", "Field" or "Eingabefeld" — the label is what the end user reads, so it must describe the field.
- CRITICAL — The 'elements' array of containers/fieldsets/pages uses 'name' values, NOT 'id' values. Example: element with name="tfVorname" and id="xi-tf-vorname" → add "tfVorname" (the name) to the container's elements array, NOT "xi-tf-vorname" (the id).
- PRESERVE every existing item exactly as-is unless the instruction explicitly targets it. Do NOT remove, rename, or reorder existing items.
- CRITICAL — When you MODIFY an existing container/fieldset/page (e.g. add a CSS class or a functionality to a fieldset), you MUST keep its 'properties.elements' array (the child name strings) EXACTLY as it was — never remove, empty, or reorder it, and never drop the child items from the 'items' array. Only the targeted properties (e.g. cssclasses, attributes) change; the children stay put. SOLE EXCEPTIONS for inserting a new element BETWEEN existing ones — (a) an INTRO/DESCRIPTION element requested "at the beginning / before the first element / ganz am Anfang / vor dem ersten Element" of a specific container/page/fieldset goes to POSITION 0 of that container's/page's 'elements' array; (b) a new element placed RELATIVE to an existing one — "unter dem Container X" / "below X" / "darunter" / "über dem Container X" / "above X" / "neben X" — becomes a SIBLING of X: insert its 'name' directly AFTER (or BEFORE, for "über"/"above") X's name in X's PARENT's 'elements' array and set its 'properties.parentid' to that PARENT, NEVER to X itself, and NEVER append it to X's own 'elements' array ("unter dem Container" means BELOW it, not inside it — only "in den Container" makes it a child). In both cases keep every other child in its existing relative order and do NOT reorder anything else.
- REMOVAL — When the user's request EXPLICITLY asks to REMOVE/DELETE existing elements (fields, buttons, containers, ...), do BOTH so the server honors the removal and does not restore the element: (1) remove the element from the top-level 'items' array AND from every container's 'properties.elements' array, and (2) list its 'properties.name' in a top-level '_removedItems' array of your output JSON (e.g. "_removedItems": ["tfOrt"]). An element removed WITHOUT being listed in '_removedItems' is treated as an accidental drop and the server may restore it.
- REMOVE-ALL — When the user asks to remove/delete ALL content — "remove all widgets/fields/buttons", "delete all fields", "empty the form", "delete all elements", "delete everything", "Lösche alle Elemente", "Lösche alle Widgets", "Entferne alle Felder", "alles entfernen", "rimuovi tutto" (in ANY language) — KEEP the first page (XPage), the header (XHeader) and the footer (XFooter) as EMPTY structural shells (their 'elements' cleared to []), remove ALL other content (fields, buttons, containers, fieldsets), list every removed element in '_removedItems', AND emit the top-level marker "_removeAll": true in your output JSON. The server strips "_removeAll" and uses it to delete the orphaned workflow paths. NEVER drop the page/header/footer.
- Do NOT include 'css', 'script', 'image', 'images', 'pagePreview', 'rendered', 'formI18n', or 'metadata' fields — they are handled separately and will be merged back. Also do NOT include any XFooter item in the items array.
- Output ONLY valid JSON. No trailing commas. No comments.
- CUSTOM JAVASCRIPT — you MAY generate a form-level custom JavaScript (e.g. a JS calculator, client-side validation, or interactive logic) and attach it to the form via the top-level `"_customScript": "<the JavaScript source, WITHOUT the surrounding <script> tags>"` marker in your output JSON. The server persists it and injects it as an inline `<script>` into every rendered form. Write plain, self-contained JavaScript (no `<script>`/`</script>` wrappers, no backticks or unbalanced braces that break JSON). It runs after the form is rendered, so read existing elements by their 'id' or 'name', attach listeners, and reference the Formcycle/`W`/`CRM` globals as needed (e.g. `CRM.Helpers.getFieldValue`, `CRM.Helpers.setFieldValue`). For a JS calculator: emit the calculator's markup via an XSpan/XFieldSet (text field 'rtevalue' or placeholder div), give the input/display elements stable ids, and provide the full working script in `_customScript` that wires the buttons to compute and set the result. When the request does NOT need custom JS, omit `_customScript`.
- The current form's existing elements are ALWAYS provided to you (the form data — all pages/containers/items with their `name`s). NEVER ask the user whether a referenced field/container already exists (e.g. "Existieren die Felder tfVorname/tfNachname bereits?" / "bereits vorhanden oder neu anlegen?") — determine it from the provided form: if the `name` is in the items, it EXISTS (reuse/modify it); if it is NOT, CREATE it as requested (e.g. as a hidden field), without asking. This applies to every field, container and DataQuery referenced by name (tfVorname, tfNachname, fdDatei, HolaQuery, …). Only ask when the request is ambiguous about WHICH element is meant (e.g. two fields with similar names) — never about existence.
- WHOLE-FORM TRANSLATION — when the user asks to translate the form / all fields / the whole form into a specific language (e.g. "übersetze das gesamte Formular ins Englische", "translate the whole form into French", "traduire le formulaire en italien"), ADD the translations for that ONE language as the per-language element translation fields — NEVER overwrite the base/default-language texts. Formcycle stores per-language element translations in each element's '"properties"."i18n"': '"i18n": { "<languageCode>": { "<property>": "<translated text>" } }' (the plain 'label'/'placeholder'/'legend'/... keep the base text). So translate EVERY user-visible text of EVERY element by writing it into that map for the requested language: 'label', an XFieldSet/page 'legend', 'placeholder', 'helptext', static XSpan text ('rtevalue'), a repeatable container's 'dynamicAddText'/'dynamicDeleteText', and other user-visible text properties — keeping the base-language values byte-for-byte identical. XSelect options: keep each option's 'text'/'value' and add '"i18n": { "<lang>": { "value": "<translated display text>" } }' on that option object. XButtonList buttons: keep 'name'/'title'/'value'/'action' and add '"i18n": { "<lang>": { "value": ..., "title": ... } }' on the button object. NEVER change the technical identifiers: every element's 'name'/'id' and the container 'elements' references, every XSelect option 'value' and button 'name'/'action', className/cssclasses (incl. CodBi_* classes), and every data-cb-func / data-cb-* name and technical value (EP placeholders, [%fieldName%] placeholders, field selectors). A field named tfVorname stays tfVorname and its German 'label' stays German — only a per-language translation is ADDED under 'properties.i18n[<lang>]' (or the option/button's own 'i18n'), which Formcycle shows when the form is displayed/edited in that language. The request changes ONLY translations: never add, remove or reorder fields and never touch layout, conditions or functionality. When "translate" appears WITHOUT a target language, ask which language (clarification) instead of guessing.

- OUTPUT-SIZE / VALIDITY — a whole-form translation re-emits the complete form AND its translations, so for a form with many elements the output becomes large. Emit the JSON COMPACTLY (no pretty-printing / no indentation) to stay within the model's output limit, and NEVER add an empty '"i18n": {}' — add '"i18n"' only to an element that actually receives at least one translation, and always finish the complete valid JSON (never stop mid-form).

- NO CODBI ELEMENT CHANGES — a translation never adds/changes/removes a CodBi element, so your whole-form-translation output MUST end with the top-level `"_codbiApplicability": { "codbiVerdict": "none", "considered": [], "applied": [] }` (like every form output, it always contains `_codbiApplicability`; for a translation the verdict is "none"). The server reads this verdict to skip its second CodBi evaluation pass — omitting it makes the server re-run the whole large form with the CodBi API, which exceeds the output limit on big forms and returns invalid JSON.

- COVER EVERY CONSUMER-VISIBLE TEXT — a whole-form translation must translate EVERYTHING the end user
  reads, not only plain labels: XPage 'header'/'subheader' (page caption + subtitle) and XFieldSet 'legend' go into 'properties.i18n[<lang>]' like a label; XSelect / XNavigationBar / radio / filterable 'options' visible texts go per entry into that entry's '"i18n": { "<lang>": { "value": "<translated text>" } }' (keep 'text'/'value'); XButtonList buttons go per button into '"i18n": { "<lang>": { "value": ..., "title": ... } }' (keep 'name'/'action'); plus placeholders, static XSpan 'rtevalue', XImage 'alt'/'title', checkbox/upload labels, dynamic add/delete texts, help texts. Leaving any visible navbar step, page caption/subcaption, button label, select option, legend or static text untranslated is a FAIL.

- MULTILINGUAL WORKFLOW MAILS — when a whole-form translation ADDS another language to the form (the
  target language differs from the form's base/default language), your JSON output must ALSO end with the
  server marker `"_workflowMailLanguages": ["<baseLanguageCode>", "<addedLanguageCode>", ...]` — a top-level
  array with the form's base language code first, then each language code this translation adds (the same
  codes written into the '"i18n"' maps). The marker tells the server to wrap every existing consumer-facing
  FC_EMAIL / FC_DOI_INIT workflow node into an FC_SWITCH branching on the workflow placeholder `[%lang%]`
  (the language the form was filled out in), keeping the original mail on the base-language branch and
  generating translated mails for the other languages. Emit it ONLY on a translation that actually adds a
  language (never on base-language-only edits or other changes). Like `_codbiApplicability`, it is a server
  instruction that is stripped before the form is saved.

## Button Actions (XButtonList)
action.page is a FORMCYCLE keyword, NOT a page name: "" (none/custom), "next" (next page), "previous" (previous page), a page name (navigate to it), or a submit command ("submit", "submitNoCheck", "submitSave", "submitSaveNoCheck", "submitPreview", "submitPreviewWindowed").

action.check=true validates the CURRENT page's fields before the action runs; action.check=false skips validation. A "next" / 'Weiter' button MUST use check=true ("next page + check") whenever the current page contains a field that can be invalid — a required field, a datatype-validated field, or a field tagged with a CodBi functionality/class (CSS class starting with "CodBi_", e.g. CodBi_People_Name, or a data-cb-func attribute). Only use check=false when the page has no such field. Submit buttons (page="submit") ALWAYS use check=true.

## Conditional Visibility / Locking / Required (hiddenif, readonlyif, requiredif) and Availability

These control when a field is hidden or locked based on another field's value. Set these as DIRECT properties on the element (NOT inside the attributes array). Formcycle uses the component's ID to reference the controlling field.

- hiddenif = the EXACT properties.id of the controlling component (e.g. the checkbox's id).
- hiddenifcomp = the Formcycle condition code (enum de.xima.fc.form.common.statics.EConditionType). The field is hidden when the condition is met:
  - 0 = MANDATORY — hidden when the controlling field HAS a value (e.g. a checkbox is CHECKED).
  - 1 = EQUAL — hidden when the controlling field's value EQUALS hiddenifvalue.
  - 2 = NOT_EQUAL — hidden when the controlling field's value is NOT EQUAL to hiddenifvalue.
  - 3 = REGEX — hidden when the controlling field's value MATCHES the hiddenifvalue regex.
  - 4 = LESS_THAN — hidden when the controlling field's value is LESS THAN hiddenifvalue (number).
  - 5 = GREATER_THAN — hidden when the controlling field's value is GREATER THAN hiddenifvalue (number).
  - 6 = BETWEEN — hidden when the controlling field's value is WITHIN the hiddenifvalue range (<min>-<max>).
  - 7 = LESS_OR_EQUAL — hidden when the controlling field's value is <= hiddenifvalue.
  - 8 = GREATER_OR_EQUAL — hidden when the controlling field's value is >= hiddenifvalue.
  - 9 = EMPTY — hidden when the controlling field has NO value (is empty). For a checkbox: hidden while the checkbox is UNCHECKED, shown once it is CHECKED.
- hiddenifvalue = the comparison value used by EQUAL/NOT_EQUAL/REGEX and the numeric codes.
- hiddenifclear controls what happens to the field's value when hidden: "false" or 0 = preserve value, "1" = clear value, "2" = disable but keep value.
- The SAME codes apply to readonlyif (gesperrt / read-only wenn) AND requiredif (Pflichtfeld wenn): readonlyifcomp / requiredifcomp work identically to hiddenifcomp, with readonlyifvalue / requiredifvalue as the comparison value. Choose by the user's wording:
  - "... soll NICHT SICHTBAR sein, wenn ..." / "only appears when ..." → hiddenif*
  - "... soll GESPERRT / schreibgeschützt / nicht änderbar sein, wenn ..." → readonlyif*
  - "... soll ein PFLICHTFELD sein, wenn ..." → requiredif* (do NOT set "required":"1" instead — that would make it mandatory unconditionally)
- hiddenifclear / readonlyifclear control the value handling while the condition is met: "false" or 0 = preserve the value, "1" = clear the value, "2" = disable but keep the value. readonlyifmode exists only on some element types — keep the designer default unless the request needs a specific locking mode.
- ALWAYS EMIT THE COMPLETE TRIPLE per conditional property: Xif (the controlling field's EXACT properties.id), Xifcomp (the EConditionType code) and Xifvalue (the comparison value) — plus Xifclear when the value handling matters. A condition without its comparison value never matches, and a condition without the controlling id does nothing.
- CRITICAL — FORMCYCLE HAS NO `disabledif` AND NO `availableif` PROPERTY: the keys do not exist in de.xima.fc.form.common.XPropertyEnum (checked against the Formcycle 8.5.3 jar) and are silently ignored by the server. NEVER emit disabledif / disabledifcomp / disabledifvalue / availableif. Map a "deaktiviert / disabled / ausgegraut wenn ..." request to ONE of:
  - readonlyif + readonlyifcomp + readonlyifvalue — the field STAYS VISIBLE but cannot be edited (the usual meaning of "deaktiviert"/"disabled"; the value is still submitted). Use this for "das Feld soll ausgegraut/nicht editierbar sein, wenn ...".
  - hiddenif + hiddenifcomp + hiddenifvalue + hiddenifclear="2" — the field is hidden AND disabled while the condition is met, its value is preserved.
  For a field that is ALWAYS locked (no condition at all) set the plain flag "isreadonly":"1"; for an always-disabled field "isdisabled":"1" (same "1"/"0" convention as ishidden / readonly).
- "Available only if" is a DIFFERENT mechanism from hiddenif: when the element shall be available/visible only for certain WORKFLOW STATUSES or USER GROUPS ("verfügbar nur im Status ...", "nur wenn der Datensatz den Status ... hat", "nur für die Benutzergruppe ..."), use the availability properties statusdependent / readonly_statusdependent / usergrouppendent (+ viewstatus / readonly_viewstatus / viewusergroup) described in the State-Based Availability section below — NOT hiddenif.
- CRITICAL: The hiddenif, readonlyif and requiredif value must be the EXACT properties.id of the controlling component.
- CRITICAL — OPTION-GATED FIELDS ("nur erscheint, wenn '<Option>' gewählt ist" / "only appears when '<option>' is selected", e.g. an upload next to "An Mitarbeiter ohne Intranetzugang senden?" that only shows when "Ja" is chosen): apply the condition DIRECTLY ON THE FIELD ITSELF (hiddenifcomp="2" NOT_EQUAL with hiddenifvalue=<the option's exact value>, e.g. hiddenifcomp="2", hiddenifvalue="yes", hiddenif=<the controlling XSelect's properties.id>) — you do NOT need to create a wrapping container for this. Only when a wrapping container already exists (or is required/requested for other reasons, see CONTAINER FOR CONDITIONALLY SHOWN FIELDS below) does the condition go on that CONTAINER instead; do NOT invent a new container just to hold the condition. This is the ONLY single hiddenif constraint that covers BOTH possible non-visible states at once, because `hiddenif` carries exactly ONE comparison value and an XSelect can be in THREE states: the chosen option ("yes"), the opposite option ("no"), or EMPTY (nothing selected — an XSelect CAN have an initial `value` preset in the form data, but need not; when none is set it starts empty). "value != yes" is TRUE for both empty and "no", so NOT_EQUAL to the CHOSEN option hides the element in every state except the chosen one. NEVER hide via hiddenifcomp="1" (EQUAL) with hiddenifvalue=<the OPPOSITE option> (e.g. "no") — that hides only the "no" state and leaves the field VISIBLE while nothing is selected (empty is a separate state, NOT the value "no"), violating "only appears when 'yes' is selected". NEVER use hiddenifcomp="0" (MANDATORY, hidden when the field HAS any value) — it hides the field even when "Ja"/"yes" IS chosen. NEVER use hiddenifcomp="9" (EMPTY) alone — it hides only the empty state, not the opposite option. The chosen option's value comes from the FORM ELEMENTS list (the option's `value`, e.g. {text:"Ja", value:"Ja"} or {text:"Ja", value:"yes"}); check whether the controlling XSelect itself has an initial `value` in the form data — but regardless, the NOT_EQUAL-to-chosen constraint is correct.

## State-Based Availability ("Available if" / statusabhängig, verfügbar für Status)

Besides the field-value conditions above, a form element's VISIBILITY and EDITABILITY can depend on the FORM RECORD'S CURRENT WORKFLOW STATE. Every workflow lane ends in an ENDING STATE (its endpoint state); that ending state IS the form record's current state until another lane changes it. These are DIRECT properties of the element (inside `properties`), NOT entries in the `attributes` array:

- `statusdependent` — the STRING `"1"` enables state-dependent availability (Formcycle compares `getString()` against `"1"`; a JSON boolean `true` is NOT recognized).
- `viewstatus` — JSON array of the workflow STATE UUIDs (new BPMN workflow: `WorkflowState.getUUIDObject().toString()`, i.e. the designer's state-list option values) in which the element IS available/shown. The element is shown ONLY while the record's current WorkflowState UUID is one of these values - the state DISPLAY NAME never matches. An entry prefixed with `[!]` (e.g. `"[!]<stateUuid>"`) EXCLUDES that state.
- `readonly_statusdependent` — the STRING `"1"` enables state-dependent read-only.
- `readonly_viewstatus` — JSON array of the workflow state UUIDs in which the element is READ-ONLY.
- User-group analogues: `usergrouppendent` + `viewusergroup`, and `readonly_usergrouppendant` + `readonly_viewusergroup`.
- STATE-BASED "DISABLED IF" ("deaktiviert, wenn der Datensatz den Status X hat" / the designer's state-based disable, also reachable through the same advanced options): there is NO `disabledif` property — the state-based disable is expressed with the READ-ONLY pair `readonly_statusdependent` (STRING `"1"`) + `readonly_viewstatus` (array of the state UUIDs): the element stays VISIBLE but cannot be edited while the record is in one of those states. Do NOT invent a new key for it. When an element must instead be NOT AVAILABLE at all in specific states, keep `statusdependent` + `viewstatus` and add those states as EXCLUDED entries prefixed with `[!]` (e.g. `"[!]<stateUuid>"`).

Rules:
- CHOOSE THE MECHANISM BY THE USER'S WORDING — THIS IS A CRITICAL DISTINCTION (the two mechanisms are NOT interchangeable). MATCH BY MEANING, NEVER BY A LITERAL KEYWORD, AND IN ANY LANGUAGE: the request may be German, English, Italian, Dutch, French, ... — recognise the CONCEPT ("available/visible" vs. "active/usable/editable"), not the exact word list below:
  - "verfügbar / sichtbar / erscheint / angezeigt / eingeblendet (nur) im Status X", "available / visible / shown / displayed (only) in state X", "disponibile / visibile solo nello stato X", "beschikbaar / zichtbaar (alleen) in status X", "disponible / visible (seulement) dans l'état X" → the AVAILABILITY pair `statusdependent` + `viewstatus`: the element is NOT RENDERED AT ALL outside those states (it disappears).
  - "AKTIV / aktiviert / nutzbar / bedienbar / bearbeitbar / freigegeben / ausgegraut / gesperrt / deaktiviert / schreibgeschützt im Status X", "active / enabled / usable / editable / greyed out / locked / disabled in state X", "attivo / attivabile / utilizzabile / modificabile / disattivato / bloccato nello stato X", "actief / bewerkbaar / ingeschakeld / uitgeschakeld in status X", "actif / modifiable / utilisable / désactivé dans l'état X" → the READ-ONLY pair `readonly_statusdependent` + `readonly_viewstatus`: the element STAYS VISIBLE but cannot be used/edited in those states.
  - "nur im Status X AKTIV / aktiviert / nutzbar / bedienbar / bearbeitbar / freigegeben sein", "only ACTIVE / USABLE / EDITABLE in state X", "solo attivo / utilizzabile / modificabile nello stato X", "alleen actief / bewerkbaar in status X", "actif / modifiable uniquement dans l'état X" → `"readonly_statusdependent":"1"` + `"readonly_viewstatus":["[!]NAME"]` where `NAME` is the state NAME the user gave (for the state GOGO the finished value is exactly `"readonly_viewstatus":["[!]GOGO"]`): read-only in EVERY state EXCEPT that one (the element stays visible everywhere but is usable only there). The `[!]` marker is MANDATORY here — `"readonly_viewstatus":["GOGO"]` means read-only IN GOGO, i.e. the exact opposite. The `[!]` is simply the first three characters OF THE SINGLE STRING — write the finished string value, never a concatenation expression (see the "ONLY USABLE IN STATE X" rule below).
  - NEVER answer an "aktiv / aktiviert / nutzbar / bedienbar / bearbeitbar / freigegeben / enabled / active / usable / editable" request (in ANY language — see the head of this rule) with `statusdependent` + `viewstatus`: that HIDES the element outside the state instead of only disabling it — the element would vanish although the user wanted it to stay visible but unusable. "Active / enabled / usable / editable" is ALWAYS the read-only pair, NEVER the availability pair.
- Emit the `*dependent` flag as the STRING `"1"` (or `"0"` for explicitly disabled) and the `*viewstatus`/`*viewusergroup` arrays as arrays of plain strings holding the STATE NAME the user gave (e.g. `["GOGO"]`; a UUID works too, but you neither need nor know it — the backend resolves names). The designer's default form template stores these flags as STRINGS (e.g. `"statusdependent":""`) and Formcycle compares the value against `"1"`, so a JSON boolean is NOT the design-time shape (the backend normalizes a boolean `true`/`false` to `"1"`/`"0"`, but emit the string yourself). Any other shape (an object, a number, a nested array) is dropped by the server.
- WRITE THE STATE **NAME** THE USER GAVE — NEVER ASK FOR A STATE UUID: put the state NAME exactly as the user wrote it into `viewstatus` / `readonly_viewstatus` (e.g. `"statusdependent":"1"`, `"viewstatus":["GOGO"]`), NEVER a UUID. The user does not know the state's UUID and neither do you, so NEVER ask for it, never say you need it and never refuse the request because it is missing. The backend resolves every plain name in `viewstatus` / `readonly_viewstatus` to the WorkflowState UUID of this form's workflow (the very state the lane of the SAME run ends in, so it exists by then) and keeps the name unchanged when it cannot be resolved. For an approve/reject flow do NOT hand-write `viewstatus` at all: emit the pending state NAME in the workflow lane's `buttonStatus` and the backend resolves it to the state UUID (creating the state if needed).
- Typical approval flow: the submit lane sends the first mail and ends in a NEW state (e.g. "Wartet auf Genehmigung"); the decision buttons carry `"statusdependent":"1"` + `"viewstatus":["<the pending-state UUID>"]` (the backend applies this from the lane's `buttonStatus`) so they appear ONLY once the record reached that state; the data fields may carry `"readonly_statusdependent":"1"` + `"readonly_viewstatus":["Wartet auf Genehmigung"]` (the state-based DISABLE) so the approver can only act on the buttons; the approve lane ends in "Genehmigt", the reject lane in "Abgelehnt".
- STATE-BASED "ONLY USABLE IN STATE X" (the "aktiv"/"enabled" wording of the rule above): if the element must stay VISIBLE in every state but be usable ONLY in state X, emit `"readonly_statusdependent":"1"` + `"readonly_viewstatus":["[!]NAME"]` (NAME = the state NAME the user gave; for GOGO the finished value is `"readonly_viewstatus":["[!]GOGO"]`) — an entry that BEGINS WITH the three characters `[!]` means "in every state EXCEPT this one", so it makes the element usable ONLY in that state. The `[!]` marker is the beginning of the string VALUE itself.
  - HARD RULE ABOUT THE SHAPE — EVERY ARRAY ENTRY IS ONE FINISHED STRING, NEVER AN EXPRESSION AND NEVER A SPLIT PAIR: write the marker and the state name TOGETHER inside the same string, e.g. `["[!]GOGO"]` (a one-element array) or `["[!]GOGO","[!]WAITING"]` (two entries), and for a UUID `["[!]d195feee-549c-44bd-afda-45096c837e7b"]`. NEVER keep the marker as its own quoted fragment standing next to the name — no plus sign between two fragments, no separate marker-only element, no quotes inside the array other than the ones delimiting the single value. Such text is INVALID JSON: the server cannot read your answer at all, so the COMPLETE form update is discarded and the previously stored (possibly INVERTED) availability stays in the form; and even after a lenient reader recovers the state name it would land as a PLAIN entry, making the element read-only/available IN that state instead of in every state EXCEPT it.
  - HARD RULE ABOUT THE MARKER'S CHARACTER ORDER — THE CLOSING BRACKET COMES BEFORE THE STATE NAME: the entry begins with the three characters opening-bracket, exclamation mark, closing-bracket, and the state name follows IMMEDIATELY after that closing bracket: `[!]GOGO` (the string's first three characters are `[!]`, the rest is the name). Do NOT wrap the whole name in the marker's brackets — the value must never look like an opening bracket followed by the exclamation mark and then the name with a trailing bracket. If the brackets are placed around the NAME instead of around the exclamation mark, the form designer does not recognise the value and shows NOTHING selected in the "Available only if" / "Disabled if" property, i.e. the negation silently does nothing.
  - Semantics (verified against `XItemDefaultReadOnlyEvaluator`/`XItemDefaultRenderedEvaluator.statusEval`, Formcycle 8.5.3): an entry that starts with `[!]` satisfies the condition as soon as the record's state does NOT match the name behind the marker (so a single such entry holds in every state except its own); plain entries (no marker) are satisfied only in the states they name; with NO entries the `*dependent` flag has NO effect at all. Therefore `"readonly_viewstatus":["[!]GOGO"]` = "read-only in every state EXCEPT GOGO" (usable only in GOGO) and `"viewstatus":["[!]GOGO"]` = "available in every state EXCEPT GOGO".
- An element with NO `statusdependent`/`usergrouppendent` (and no `readonly_*` pair) is available AND editable in every state (the default) — only set these when the element must appear / be usable in specific states.

## CONTAINER FOR CONDITIONALLY SHOWN FIELDS

When the prompt describes a field that should be shown or hidden based on a condition (wenn...dann..., if...then...), you MAY apply the show/hide condition directly on the field itself (hiddenif / hiddenifcomp / hiddenifvalue as direct properties) — a wrapping container is NOT required for the condition to work. Only when a container ALREADY exists around the field (pre-existing in the form, or explicitly created/requested for other layout reasons) does the container become the target of the conditional functionality — in that case put the hiddenif properties ON THE CONTAINER, not on the inner field, because the empty container would otherwise remain visible and the hidden field would still leave a visible gap. Do NOT invent a new container purely to hold a show/hide condition when the prompt did not ask for one.

EXCEPTION — BundID fsBKAllDaten: When the prompt asks to show/hide BundID/Bürger-Services fields based on any condition, do NOT create a new container. The existing XFieldSet named 'fsBKAllDaten' is already the container for all BundID fields. Instead, add the show/hide properties ('hiddenif', 'hiddenifcomp', 'hiddenifvalue') directly to the fsBKAllDaten element.

## REPEATABLE CONTAINERS

To make a field group repeatable (the user can add/duplicate rows via a '+' button - in ANY language), wrap the fields in an XContainer or XContainerInvisible with "dynamic":"1" (REQUIRED — this is what makes the container repeatable; without it the container is NOT repeatable) plus "dynamicMinSize" (min rows, default 1), "dynamicMaxSize" (max rows, default 10), "dynamicAddText" (the '+' button label, e.g. '+ Thema hinzufügen'), "dynamicDeleteText" (delete button label). The container is itself an item in the root 'items' array; its 'elements' array lists the inner field names; the page's 'elements' array references ONLY the container's name (do NOT list the inner fields directly on the page). CRITICAL - Do NOT add ANY extra element (button, text, span or label such as 'Thema hinzufügen') inside the container to represent the add action: the dynamic container renders its own add/delete buttons via dynamicAddText/dynamicDeleteText. A missing dynamic:"1" or a manual add-button without a dynamic container is WRONG.

CRITICAL - NEVER NEST REPEATABLE CONTAINERS. A dynamic container ("dynamic":"1") must NOT contain another dynamic container ("dynamic":"1") — Formcycle rejects such a form ("Ein wiederholtes Element darf keine anderen wiederholten Elemente enthalten"), so the form fails to load and the designer shows it empty. Formcycle has exactly ONE repetition level. If the request implies two repetition levels (e.g. several weekdays/days each with several Von-Bis time blocks, or sections each with several entries), express it with a SINGLE dynamic container whose each row carries a weekday dropdown/select PLUS a FIXED set of the repeated fields (e.g. up to 10 'Von/Bis' time-field pairs; unused ones simply stay empty), or use ONE repeatable row per entry (weekday + one Von/Bis). Never create a second dynamic container inside a dynamic container; a plain (non-dynamic) XContainer nested inside a dynamic container is allowed. WRAPPING AN EXISTING REPEATABLE TO ADD A PANEL: when the request is to put an existing repeatable container (e.g. the weekday container) inside a NEW wrapper that becomes the collapsible panel ("Der Container für die Wochentage soll nicht mehr selbst das klappbare Panel sondern ein Container um den Wochentage Container"), the NEW wrapper MUST be a plain, NON-dynamic XContainer (NO "dynamic" property) that lists the EXISTING repeatable container in its "elements"; keep the existing container's name/id/"elements"/"dynamic":"1" EXACTLY as they are and put data-cb-func=html.panel on the WRAPPER. NEVER give the new wrapper "dynamic":"1" (or copy the inner container's dynamic* properties) — repeating the wrapper creates a forbidden repeatable-in-repeatable which the server must flatten and which risks dropping the wrapper's fields.

WRAPPING A CONTAINER IN A NEW PANEL WRAPPER — FOLLOW THE PROMPT'S INTENT: when the prompt says the ORIGINAL container shall NO LONGER be the panel ("...soll nicht mehr selbst das klappbare Panel sein sondern ein Container um den ... Container"), the panel functionality MOVES — put data-cb-func=html.panel (plus its data-cb-* parameters) on the NEW wrapper and REMOVE all of them from the ORIGINAL container so it becomes a plain container. CREATE EXACTLY ONE NEW WRAPPER CONTAINER (never two — do NOT add BOTH a new "...Panel" container AND a separate new "...Wrapper" container around the same original container); the single new outer container holds the EXISTING container unchanged. THE NEW WRAPPER MUST BE A PLAIN, NON-REPEATABLE CONTAINER: give it NO "dynamic" property (or "dynamic":"0"); ONLY the EXISTING container keeps "dynamic":"1" when it was repeatable. NEVER copy the repeatable flags (dynamic / dynamicMinSize / dynamicMaxSize / dynamicAddText / dynamicDeleteText) onto the wrapper — a repeatable wrapper around a repeatable container is a forbidden repeatable-inside-repeatable that the server must flatten. When the prompt does NOT say so, leave the original container as it is and only add the one wrapper — but NEVER nest a container panel (html.panel on an XContainer) inside another container panel (that renders a panel inside a panel); nested panels use CodBi_HTML_Panel_Flat / CodBi_HTML_Panel_Minimal on FIELDSETs. Never drop a panel the prompt did not ask to remove, and never leave the same panel duplicated on both. TO MAKE THE REMOVAL STICK you MUST re-emit that container's ENTIRE properties.attributes array WITHOUT the html.panel entry (drop data-cb-func=html.panel and every data-cb-* panel parameter); merely OMITTING the attributes key makes the server restore the original attributes from the saved form, so the panel returns. ALSO re-emit its cssclasses WITHOUT any UI.Panels panel-type class (CodBi_HTML_Panel_Standard/Flat/Index/Minimal, CodBi_HTML_Panel_NoCordion) — those work only on a FIELDSET, never on a container. SUMMARY CHECK BEFORE FINISHING: exactly ONE new wrapper container; it is NON-repeatable (NO "dynamic"); the ORIGINAL container has NO html.panel and NO panel class; NO container panel stacked inside another container panel; NO repeatable container inside another repeatable container.

WORKED EXAMPLE — prompt "Der Container für die Wochentage soll nicht mehr selbst das klappbare Panel sein sondern ein Container um den Wochentage Container." is the EXACT wrap-the-panel-outward case: the ORIGINAL repeatable container `coOpeningHoursPanel` (dynamic:"1", currently carrying data-cb-func=html.panel + its header/css params, elements=["selWeekday","tfFromTime","tfToTime"]) must NO LONGER be the panel. Correct output: create EXACTLY ONE new wrapper XContainer `coOpeningHoursPanelWrapper` that (a) lists the ORIGINAL `coOpeningHoursPanel` in its `elements`, (b) gets `parentid` = the accordion's id and REPLACES `coOpeningHoursPanel` in the accordion's `elements` array, and (c) carries data-cb-func=html.panel plus ALL of the panel parameters. The ORIGINAL `coOpeningHoursPanel` keeps its name/id/elements and its `dynamic:"1"` (and dynamic* props), gets `parentid` = `coOpeningHoursPanelWrapper`'s id, and MUST be re-emitted with an EXPLICIT EMPTY `"attributes": []` array — the key present but empty, NEVER omitted, because a missing `attributes` key makes the server restore the old html.panel. Do NOT create a second plain wrapper in between and do NOT leave the panel on the inner container. Resulting chain: accordion → `coOpeningHoursPanelWrapper` (html.panel) → `coOpeningHoursPanel` (plain, dynamic, attributes:[]) → selWeekday/tfFromTime/tfToTime.

## MAKE EXISTING AREAS/SECTIONS COLLAPSIBLE BY CONVERTING THEM IN PLACE

A request such as "Alle Bereiche im Formular sollen klappbar sein und, bis auf den ersten Bereich, anfangs zugeklappt sein" (or any "make the sections/areas/panels collapsible / aufklappbar / klappbar / accordion" request) targets containers/fieldsets that ALREADY EXIST. Convert each of them IN PLACE: keep the SAME item with the SAME `name` and the SAME `id`, KEEP its `elements` array EXACTLY as it is (every child field name stays in it), and KEEP every child item in your output — only ADD the panel class / folding attribute. Do NOT delete the existing containers and do NOT create new, empty panels. A converted panel MUST still list and contain ALL of its original child fields. Omitting the children, or emitting a panel/fieldset with `"elements": []`, renders an EMPTY form.

## FORMCYCLE output rules for form element identifiers

FORM ELEMENTS entries have: 'technicalId' (always), 'displayText' (visible label/text), 'type' (e.g. XTextField, BUTTON), and optionally: 'required' (boolean), 'placeholder', 'options' (for XSelect), 'actionPage' (for BUTTON).

'technicalId' is an ARBITRARY internal database key. 'displayText' is what the user sees. The user's prompt refers to 'displayText'. Find the matching element, then copy its 'technicalId' EXACTLY. NEVER use a 'displayText' value in the output. NEVER guess or invent a technicalId.

Elements with type 'BUTTON' are individual clickable buttons. For triggerParams.buttonName always use the 'technicalId' of the individual BUTTON whose 'displayText' matches — never use a container's id.
